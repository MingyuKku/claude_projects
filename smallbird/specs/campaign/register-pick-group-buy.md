## 1. 목적과 범위

- PICK형을 구독한 광고주가 **PICK형 공구형 캠페인**을 브랜드형과 같은 마법사로 등록하고, 빅버드 머니로 결제(= 승인 요청)합니다. PICK형 미구독 광고주는 같은 마법사로 데모 등록합니다(§3 데모).
- 브랜드형과 다른 곳: 단계 구성(진행 조건 자리에 **공동구매 조건 설정**), 캠페인 유형 제품발송형 고정, 부가서비스 AI 포스팅 가이드 1개, 결제·등록 내역 문구.
- **공구샵 개설 단계는 이번 범위에서 빠집니다**(사용자 결정, 시안도 "To Be Determined" 빈 프레임 `14184:95110`).
- 모집형 공구형(요구명세서 9번 탭)은 범위 밖입니다.

### 시나리오

1. 캠페인 개설에서 PICK형(구독 중) → **공구형** 상품 카드를 누르면 `/campaign/register?type=pick&product=group-buy`로 와서 공구형 캠페인을 만들고(A-1 `productType: GROUP_BUY`) `/campaign/register/:campaignId?step=campaign-info`로 바뀝니다(REQ-4-0019 "모집형/PICK형과 브랜드형/공구형 조합을 등록 초기값으로 전달"). 지금 공구형 카드의 "준비 중" 토스트를 이 진입으로 바꿉니다([status](./status.md) 갱신).
2. 1단계 필수값을 채우고 "다음"을 누르면 2~8단계가 열리고, 이후 이동·저장·결제·승인 흐름은 브랜드형과 같습니다.
3. 다시 들어올 때(작성 경로·등록 내역) 서비스·상품 유형은 주소가 아니라 서버 캠페인 값(`serviceType`·`productType`)으로 정합니다.

- 시안 사이드바의 6번 "공구샵 개설"은 **단계 배열에서 빼고 1~8로 번호를 다시 매깁니다**(사용자 결정 2026-11-20). 사이드바·주소·결제 전 검사·등록 내역 섹션 번호에 모두 없습니다. 공구샵이 나오면 단계 정의 배열에 끼워 넣고, slug 주소라 기존 주소는 바뀌지 않습니다.
- **진행 조건 설정(`conditions`) 단계가 없습니다**: 포스팅 유지기간·2차 저작권을 받지 않습니다(시안 사이드바·등록 내역 섹션 모두 없음). `?step=conditions`로 오면 잘못된 slug처럼 "아직 완료하지 않은 첫 단계"로 엽니다.
- 단계 정의는 `getRegisterSteps(serviceType, productType)`로 상품 유형까지 받아 공구형 배열을 돌려줍니다(register §3 "단계 구성"). 1단계 통과 전 2~8 비활성, 입력 중·미입력 경고 아이콘, 선택 단계(부가서비스) 예외는 브랜드형 규칙을 그대로 씁니다.

### 1단계 캠페인 정보

- 구성(코드·이전 캠페인 불러오기·캠페인명·브랜드명·캠페인 유형·날짜)은 브랜드형과 같습니다.
- **캠페인 유형은 제품발송형 고정**입니다(PC·TAB 시안은 "제품 발송형" 토글 1개만, REQ-11-0010). 토글 1개를 선택 상태로 보여 주고 누를 수 없게 둡니다. 만들 때 제품발송형으로 채우므로 **유형 변경 알럿과 2단계 초기화는 공구형에 없습니다**. MO 시안의 유형 토글 3개는 잔재입니다.
- 날짜 라벨은 **"공동구매 희망 시작 일자"**(PC·TAB, MO "캠페인 희망 시작 일자"는 잔재)이고, 고르는 칸은 브랜드형처럼 1칸입니다.
- **종료일은 시작일 + 60일로 자동**이고, 도움말은 "종료 날짜는 자동으로 60일 후로 세팅됩니다."입니다. 근거: 브랜드형은 30일이라, 공구형에서 디자이너가 일부러 바꾼 값은 PC의 "60일"뿐입니다. TAB·MO 도움말과 결제 예시 "(30일)"은 브랜드형을 복사하면서 남은 잔재로 봅니다(MO 1단계에 유형 토글 3개가 남은 것과 같은 패턴). 요구명세서 11번 탭의 "최대 1주일·종료일 직접 선택"(REQ-11-0006·0012)은 시안과 다르므로 시안을 따릅니다. 종료일 값은 1단계 저장 응답(`endDate`)을 그대로 씁니다. 서버도 공구형에서 60일로 계산합니다(2026-11-20 스테이지 배포: 저장 응답·불러오기·stage 테스트 승인. 운영 앱 승인은 운영 앱 연결 때 확인).
- 시작일은 브랜드형처럼 **오늘 이전만 막습니다**. 11번 탭의 "월정액 이용기간 안에서 시작"은 10번 탭 옛 판과 같은 문구입니다. 10번 탭은 개정 때 이 문구를 "구독 기간 안 매칭 완료"로 바꿔 등록 단계와 무관해졌고(register §3 1단계), 시안에도 제한 주석이 없습니다.
- 이전 캠페인 불러오기 대상은 **PICK형 공구형 캠페인**(데모 포함)입니다(REQ-11-0013, REQ-4-0024 "동일한 서비스 유형 및 브랜드형/공구형 조합", 목록 조회에 `productType`을 이미 넘김). 복사 범위는 1~6단계 입력값 전체(공동구매 조건 포함)이고 나머지 규칙은 브랜드형과 같습니다.

"무관"은 브랜드형 "전체"(`All`)와 같은 규칙입니다(다른 주제와 함께 고르지 않음, register P-30). 서버에 저장된 값 중 이 9개에 없는 코드는 선택하지 않은 것으로 읽고 다음 저장 때 빠집니다.

"무관"은 다른 연령대와 함께 고를 수 없습니다(주제와 같은 규칙). 기본 선택은 시안대로 인스타그램·여성·연령대 "무관"·주제 "무관"입니다(브랜드형은 10대·뷰티). 숏츠·릴스의 제목 해시태그 칸 여부는 기획 확인 전입니다(P-G5 ②).

### 4단계 공동구매 조건 설정 (새 단계)

| 필드 (모두 필수) | 입력 | 규칙 |
|---|---|---|
| 공동구매 제품명 | 텍스트 | 협찬제품명과 별개로 직접 입력, 최대 100자, 공백만 있으면 빈 것으로 봄(서버 `groupBuyingProductName`) |
| 공동구매 상품 대분류 | Select | 서버 목록(`GET /v3/campaign/product-categories`, 대분류 안에 중분류를 넣은 트리 한 번)을 번호로 고르고 이름은 서버 값 그대로 보여 줍니다(번역하지 않음). 바꾸면 중분류를 비웁니다 |
| 공동구매 상품 중분류 | Select | **대분류에 딸린 2단 구조**입니다(시안의 Select 두 개, 예시 "여행/문화" > "호텔/팬션 예약"). 대분류를 고르기 전에는 비활성(Select `State=Disabled`)이고, 선택지는 고른 대분류에 딸린 것만 보여 줍니다 |
| 권장소비자가 | 숫자 + "원" | 협찬제품 금액과 별개로 직접 입력, 숫자만·천 단위 표시·1원 이상(서버 `recommendedConsumerPrice`, 서버는 0 이상도 저장하지만 결제가 1원 이상을 요구) |
| 공동구매가 | 숫자 + "원" | 브랜드형 금액 칸 규칙(숫자만, 천 단위 표시, 1원 이상, 상한 없음). 서버 필드 이름은 `purchasePrice`입니다. 권장소비자가보다 커도 되는지는 P-G3이고, 답 전에는 검사하지 않음(서버도 검사하지 않음) |

- **공동구매 제품명·권장소비자가는 이 단계에서 직접 입력합니다**(사용자 결정 2026-11-24). 처음에는 빈 칸이고 2단계 값을 채워 주지 않으며, placeholder는 시안 원문("공동구매 제품명을 입력해 주세요."·"권장소비자가를 입력해 주세요.")입니다. 두 값의 필수 검사와 사이드바 미입력 경고는 이 단계에 붙고, 2단계의 협찬제품명·금액 검사는 브랜드형과 같습니다.

- 배치: PC·TAB은 카드 하나에 제품명 한 줄 → 대분류 | 중분류 → 권장소비자가 | 공동구매가(2열), MO는 제품명 → 대분류 → 중분류 → 권장소비자가 → 공동구매가(1열). **공동구매가 입력 아래에 구분선과 안내 두 줄**이 붙습니다(시안 3.0.1): "네이버 쇼핑 검색 기준 최저가보다 최소 10% 이상 저렴하게 설정하는 것을 권장합니다." · "공동구매가는 공동구매 진행 시점의 네이버 쇼핑 검색 최저가에 따라 변경될 수 있습니다."(시안의 "다라"는 오타라 "따라"로 씀). 안내는 공동구매가와 같은 열(PC·TAB은 오른쪽 열, MO는 공동구매가 바로 아래)에 있습니다. 새 시안은 PC 프레임뿐이라 TAB·MO는 2단계 안내 박스와 같은 규칙으로 두고 시안을 받으면 대조합니다(D-G6). 셀렉트는 브랜드 선택과 같은 디자인 시스템 `Select`입니다. PC·TAB에서는 팝오버, MO에서는 바텀시트로 열립니다(register §3 하위 화면 규칙, 페이지 주석 "인터랙션은 PICK형/모집형과 동일").
- 라벨·placeholder는 PC 원문을 모든 기기에 씁니다(MO의 "공구상품 대분류/중분류", "대분류를 선택해 주세요.", "공동구매가 가격을…"은 잔재).
- 결제 전 검사에서 제품명·대분류·중분류·권장소비자가·공동구매가가 비면 이 단계에 사이드바 미입력 경고가 붙습니다. 반려 후 수정 모드에서는 결제 금액과 무관해 **고칠 수 있습니다**.
- 저장은 `PUT /v3/campaign/{id}/group-buying-conditions`이고 서버에 있습니다(`{groupBuyingProductName, productCategoryIdx, productMiddleCategoryIdx, recommendedConsumerPrice, purchasePrice}`, §5). 서버는 중분류를 비워도 저장하지만 결제는 공구제품명(공백만 불가)·대분류·중분류·권장소비자가 1원 이상·구매 금액 1원 이상을 모두 요구하므로 프론트도 다섯 값을 모두 필수로 봅니다.

### 6단계 부가서비스

- 카드는 **AI 포스팅 가이드 1장**입니다(시안·REQ-9-0019 "공구형은 원고컨펌 절차가 없음"). 원고컨펌은 고를 수 없고 결제·등록 내역에도 없습니다. 반려 후 수정 모드에서 잠그는 것은 브랜드형과 같습니다.

### 8단계 결제

- 카드 구성·충전·결제 흐름·오류 처리는 브랜드형과 같습니다. 결제 금액은 **AI 포스팅 가이드만**(부가세 포함 11,000원, 안 고르면 0원)입니다.
- 캠페인 요약: 서비스 유형 **"PICK형 공구형"**(시안 "PICK형 브랜드형"은 잔재, 기존 `pickGroupBuy` 라벨), 캠페인 유형 "제품발송형", 리워드 "제품 제공 ({협찬제품 금액}원 상당)", 캠페인 기간(서버 시작·종료일, 일수는 실제 차이). "구매 지원금" 행·"(건별 5,000원 * 모집인원 400명)"·TAB·MO의 "AI 원고 컨펌" 행은 잔재라 그리지 않습니다. 공동구매가·권장소비자가는 요약에 넣지 않습니다(시안에 없음).

## 4. 배치

- 새 슬라이스는 없습니다. 브랜드형 마법사(`features/register-campaign`·`entities/campaign`·`pages/campaign-register`)에 상품 유형 분기를 더합니다.
- 서비스·상품 유형별 단계 배열과 단계 화면 컴포넌트만 늘리고, 마법사 골격·저장·주소는 그대로입니다(register §3 단계 구성). 단계 slug 목록(`CAMPAIGN_REGISTER_STEPS`)에 `group-buy`를, 초안 묶음(`CampaignDraftStep`)에 `groupBuy`를 더합니다.
- 마법사 store는 이미 `productType`을 가지므로 단계 배열·1단계 유형 고정·결제 요약·등록 내역 섹션은 그 값으로 고릅니다. 공구형 전용 화면 분기를 컴포넌트 곳곳에 흩지 말고 단계 정의(배열)와 단계 컴포넌트 안에 둡니다.
- 대·중분류 목록은 `entities/campaign/api`의 `useProductCategories`(마법사·등록 내역이 함께 씀)로 한 번 읽어 캐시합니다.

## 5. 데이터 흐름의 예외

- 공동구매 조건 API는 서버에 배포됐습니다(2026-11-20, 스웨거 V3-캠페인): 저장 `PUT /v3/campaign/{id}/group-buying-conditions`, 상품 카테고리 `GET /v3/campaign/product-categories`, 조회(A-3)의 `groupBuyingConditions`(공구제품명·권장소비자가 포함. 협찬제품명·금액은 `product`의 별개 값), 결제·재승인·데모 작성 완료의 `missingSteps` 이름 `group-buying-conditions`, 공구형 생성(`productType: GROUP_BUY`)·목록 필터·불러오기(공구형 조건 포함, 원본이 브랜드형이면 비움). 공구형이 아닌 캠페인에 저장하면 `400 SERVICE_TYPE_MISMATCH`입니다.
- 프론트는 이 API를 그대로 쓰고 Zod로 검증합니다.
- **서버 처리(2026-11-20 13:54 스테이지 배포)**: ① 종료일은 공구형이 시작일 + 60일(브랜드형 30일). ② 공구형은 결제·재승인·데모 작성 완료에서 `conditions`(포스팅 유지기간·2차 저작권)를 검사하지 않고 `info`·`product`·`influencer`·`group-buying-conditions`·`intro`만 필수로 봅니다. 공구형이 두 값을 정말 받지 않는지는 기획 확인(P-G4) 뒤 다시 정합니다.

## 6. 다국어

- namespace는 기존 `features/register-campaign`·`entities/campaign`입니다. 브랜드형과 문구가 다른 곳(1단계 날짜 라벨·도움말)은 같은 키에 상품 유형 접미사를 붙여 나눕니다(예: `info.startDate.label.brand` / `.groupBuy`).

## 9. 검증

- `pnpm verify`. 라우트·진입 파라미터를 바꾸므로 `pnpm build`도 돌립니다. 구현 때 [status](./status.md)(공구형 카드 진입·데모)와 `docs/pages.md`(`/campaign/new`·`/campaign/register` 행)를 같이 갱신합니다.
- 화면 확인(PC 1440·TAB 768·MO 360, stage 서버에 붙인 개발 서버, 시안 대조, `?lng=en` 넘침)
  1. 개설 → PICK형 → 공구형 카드 → `/campaign/register?type=pick&product=group-buy` → 작성 경로로 교체. 브랜드형 카드는 그대로 브랜드형으로 가는지, `product`가 잘못되면 not-found인지 봅니다.
  2. 사이드바가 8단계(공구샵 개설·진행 조건 없음, 공동구매 조건 설정 4번, 부가서비스 6번)이고, `?step=conditions`면 첫 미완 단계로 열리는지 봅니다.
  3. 1단계: 유형 토글이 "제품 발송형" 하나로 선택·고정, 날짜 라벨 "공동구매 희망 시작 일자"·도움말, 불러오기 목록이 PICK형 공구형만인지 봅니다.
  4. 2단계는 제품발송형 화면만(사이드바·제목 "협찬 제품 정보 입력"), 3단계는 플랫폼 6개 순서·"네이버 블로그"·주제 9개("무관" 상호 배타), 4단계는 제품명·권장소비자가를 직접 입력하고(2단계 값과 별개, 비면 4단계에 경고) 공동구매가 아래 안내 두 줄, 대분류를 바꾸면 중분류가 비고 대분류 전 중분류 비활성·금액 천 단위 표시·MO 바텀시트를 봅니다. 저장 후 새로고침하면 값이 돌아오는지(목) 봅니다.
  5. 6단계 카드가 AI 포스팅 가이드 1장, 8단계 서비스 유형 "PICK형 공구형"·구매 지원금·원고컨펌 행 없음·금액(11,000원 / 0원)을 봅니다. 4단계를 비운 채 "결제하기"를 누르면 미입력 알럿 → 4단계로 가는지 봅니다.
  6. 등록 내역: 섹션 1~8 번호와 4번 공동구매 행, 반려 수정 모드에서 4단계를 고칠 수 있고 6·8단계는 읽기 전용인지 봅니다.
  7. 데모: PICK형 미구독 계정으로 공구형 "데모 캠페인 등록" → DEMO 뱃지·안내·"완료" → 기본정보 데모 안내까지 브랜드형과 같은지 봅니다.
