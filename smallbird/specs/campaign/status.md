# 캠페인 현황 `/campaign` · 캠페인 개설 `/campaign/new`

> Figma 파일 `a4XCjbdpUcHsm71V1ZucPb`의 "✔️ 캠페인" 페이지(`7370:89603`), Change log 3.0.3(2026-11-11, 2026-11-13 재스캔으로 node ID가 `12928:*`·`13307:*`로 새로 매겨짐) 시안과 요구명세서 `(VER2026)빅버드_v3_요구명세서.xlsx`의 4번(캠페인 개설)·5번(캠페인 현황) 탭 **개정판(2026-11-12, REQ 번호가 새로 매겨짐)**, 그리고 사용자 결정(2026-11-10·11-12)을 기준으로 합니다. **요구명세서와 시안이 어긋나면 시안을 따릅니다**(사용자 결정). 명세서에만 있고 시안에 진입점이 없는 기능은 만들지 않습니다.
> 6번(등록 중 캠페인)·7번(진행 중 캠페인) 탭은 지금 시안과 다른 옛 화면 구성(별도 목록·상태 필터·"완료된 캠페인" 영역)을 설명하므로, 시안에 없는 정보(삭제 확인 문구 등)를 보충할 때만 씁니다.
> 화면별 문구 원문·디자이너 주석·node 대응은 로컬 캐시에 있습니다(로컬 전용): `.claude/figma-cache/campaign.md`(시안), `req-campaign-status-v2.md`(4·5번 탭 개정판 원문, 이 문서의 REQ-4·5 번호는 여기서 찾습니다), `req-campaign-status.md`(2026-11-10 옛 판 4~7번, 6·7번 탭 참고용).
> 8단계 등록 마법사와 등록 내역은 [register](./register.md)가 기준입니다. 이 문서는 그 앞(개설)과 바깥(현황 목록)만 다룹니다.

## 1. 목적과 범위

- 광고주가 **자기 캠페인을 진행 단계별로 모아 보고**(현황), 새 캠페인을 만들 때 **서비스와 상품을 고른 뒤 등록 마법사로 들어갑니다**(개설).
- 용어: **개설**은 서비스(모집형/PICK형)와 상품(브랜드형/공구형)을 고르기만 하는 화면이고 저장하는 것이 없습니다. **등록**은 고른 유형으로 내용을 쓰고 결제해 승인을 요청하는 8단계 마법사(`/campaign/register`)입니다. 시안은 개설 화면의 섹션 제목과 진입 버튼을 "캠페인 등록"이라고 부르지만, 문서와 코드에서는 둘을 구분합니다.
- **API는 서버에 구현돼 연결했습니다**(2026-11-18 기준). 목록·삭제는 백엔드가 [캠페인 등록 API 요구 명세](https://claude.ai/artifact/UGv9ZruAw7qhJyzQopAHfU)에 함께 넣었습니다(2026-11-12: 목록 A-2, 삭제 A-4). 그래서 따로 만들려던 "캠페인 현황 API 요구 명세"는 만들지 않고, 현황에 필요한 응답 필드는 그 문서 A-2에 프론트 요청으로 적었습니다(§5). 개설의 구독 상태는 구독 API(`entities/subscription`)를 씁니다. 목은 쓰지 않습니다(전체 목 모드는 2026-11-24에 없앴고, 서버 없이 도는 테스트는 `serverApiV3`를 가짜로 바꿔 검증합니다).
- **두 화면은 개발 서버·stage·prod 빌드에서 모두 열립니다**(2026-11-18 사용자 결정으로 "개발 서버에서만"을 풀었습니다. prod 배포 때는 기능이 모두 끝나 있을 것이라 막지 않음). 진입점(LNB "캠페인"·"캠페인 등록하기", 홈 "캠페인 등록/운영" 카드)도 같이 켭니다.

| 진입점 | 도착 |

### 시나리오

1. LNB "캠페인"으로 들어오면 전체 탭이 열립니다. 탭(전체·등록 중·승인 대기/반려·진행 중·종료), 캠페인 유형 필터, 캠페인명·브랜드명 검색으로 목록을 좁힙니다. PC·TAB·MO 모두 끝까지 스크롤하면 다음 묶음을 이어 불러옵니다.
2. 행의 바로 가기로 이어서 작업합니다. 등록 중은 "작성하기"로 등록 마법사(작성 완료한 데모도 "작성하기"이고 기본 정보로 감), 승인 대기는 "등록 내역", 승인 반려는 "반려 사유"로 등록 내역(`/campaign/:campaignId`, 보완 요청 메시지가 보임)으로 갑니다. 승인 대기·승인 반려·진행 중·종료의 오른쪽 문서 아이콘도 등록 내역(기본 정보)으로 갑니다. "캠페인 관리"·"결과 확인"은 PICK형 브랜드형이면 캠페인 진행 화면([progress](./progress.md))으로 가고, 그 밖의 유형은 준비 중 토스트를 띄웁니다(2026-11-26).
3. 등록 중 캠페인(데모 포함)은 휴지통 아이콘으로 지웁니다(확인 알럿 → 삭제 → 목록 갱신). 승인 대기·승인 반려는 지울 수 없고, 등록 내역에서 승인 요청을 취소해 등록 중으로 돌린 뒤 지웁니다(REQ-5-0033).
4. "+ 캠페인 등록하기"로 개설에 오면 서비스 카드 4개(모집형·PICK형·라이브형·어필리에이터형)가 보입니다. 구독 중인 서비스 카드를 누르면 아래에 그 서비스의 상품 카드(브랜드형·공구형)가 나오고, **브랜드형 카드를 누르면** `/campaign/register?type=recruit|pick`으로, **PICK형 공구형 카드를 누르면** `/campaign/register?type=pick&product=group-buy`로 갑니다([register-pick-group-buy](./register-pick-group-buy.md)). 모집형 공구형은 준비 중 토스트입니다.
5. 구독하지 않은 서비스는 "구독하기"로 마이페이지 구독에 가거나, "데모 체험하기"로 데모 상품 카드를 볼 수 있습니다. 데모는 횟수 제한 없이 여러 개 만들 수 있고, 구독 중인 서비스에는 데모 경로가 없습니다(REQ-4-0010·0022). PICK형 "데모 캠페인 등록"은 등록 마법사의 데모 모드로 갑니다([register](./register.md) §3 데모 모드, 사용자 결정 2026-11-12). PICK형 공구형의 데모는 `?type=pick&product=group-buy&demo=true`로 갑니다. 모집형 데모 캠페인 등록과 모집형 공구형은 준비 중 토스트입니다.

### 범위 안 화면

| 경로 | 화면 |
|---|---|
| `/campaign` | 현황. 탭·필터·검색은 쿼리(`?tab=&type=&q=`)로 두어 새로고침·뒤로가기·공유에도 유지합니다 |
| `/campaign/new` | 개설. 고른 서비스는 쿼리(`?service=recruit\|pick`)로 둡니다 |

`/campaign/new`는 기존 `/campaign/:campaignId`(등록 내역)와 겹쳐 보이지만, React Router는 고정 경로를 동적 경로보다 먼저 맞춥니다.

## 2. Figma 기준 노드

화면·상태별 노드 ID(PC 1440 · TAB 768 · MO 360)는 `.claude/figma-cache/campaign.md`에 있습니다. 캔버스는 가로로 "캠페인 현황"(x 3759~12377)·"캠페인 개설"(x 13101~18473) 두 구역입니다.

- 프레임 이름은 믿지 않습니다. 개설 프레임과 일부 MO 현황 프레임이 모두 `… / Campaign Registration`이고, MO 필터 화면은 `MO / Subscribe`입니다. 구역 제목과 화면 내용으로 구분합니다.
- `Guide Caption/Inform`은 디자이너 주석입니다. 개설 시안의 숨은 보조 문구 "LNB에서 빅버드 문의 클릭 시…"는 다른 화면에서 복사된 잔재라 따르지 않습니다.
- 시안끼리 다르면 **PC 시안**을 따르고 차이는 §8 디자인 요청에 모읍니다(등록 스펙 D-10과 같은 기준).

| 카드(TAB·MO) | 썸네일·이름·부제 → [바로 가기(넓게) + 아이콘 버튼] → 구분선 → "진행 단계" 배지 · "캠페인 유형" · "캠페인 기간" 3행입니다(`9853:936150`). 아이콘이 바로 가기 **오른쪽**에 옵니다(시안 `13307:113160`, PC 표도 오른쪽) |
| MO 필터 | "필터" 버튼 → "필터 검색 설정" 화면(`9853:936160`, 캠페인 유형 Select 하나, "초기화"·"적용하기")입니다. 공통 `list-filter`로 열고 `?panel=filter`이며 뒤로가기로 닫힙니다. MO에는 새로고침 아이콘이 없습니다(시안) |
| 빈 상태 | 탭·툴바는 그대로 두고 세 경우로 나눕니다(REQ-5-0030~0032, 문구 §6). ① **계정에 캠페인이 하나도 없음**(전체 탭 + 검색어·필터 없음 + 0건): 시작 일러스트 + "첫 캠페인을 시작해 보세요!"(3.0.4 시안 `14094:687914` 등, 본문 버튼 없이 툴바의 등록 버튼만 둠). 이 상태에서 **검색어·필터를 걸면**(전체 탭) 조건 없는 전체 목록이 0건인지 한 번 더 확인해 계정이 비어 있으면 목록 아이콘 + "진행 중인 캠페인이 없습니다."(`14094:687938`)로 보입니다. ② **상태 탭에 없음**: 표 안에 아이콘 + 탭별 문구(진행 중 탭은 시안 "진행 중인 캠페인이 없습니다."), 버튼 없음. ③ **계정에 캠페인이 있는데 검색·필터 결과 없음**: 검색어가 있으면 "'{검색어}'에 대한 결과가 없습니다."(시안), 필터만이면 조건 결과 없음 문구, 둘 다 검색·필터를 바꾸라는 안내, 버튼 없음. ①·② 탭별·③ 필터만 문구는 시안이 없어 D-5 |
| 불러오기·오류 | 처음 불러오는 동안 행 자리 스켈레톤(`skeleton-presets`), 실패하면 기존 목록 오류 패턴(다시 시도)입니다. 시안 없음 |
| Sub ID | 서버가 할당한 캠페인만 줍니다. 할당된 Sub ID에게는 "+ 캠페인 등록하기"(본문·LNB)·"작성하기"·휴지통을 숨기고, 등록 내역·반려 사유·목록 아이콘은 보입니다(사용자 결정, P-3). 작성을 마친 데모는 조회할 수 있어 "작성하기" 대신 "등록 내역"으로 기본 정보를 엽니다 |

### 개설

| 항목 | 결정 |
|---|---|
| 셸 | 현황과 같은 `AppShell`, 헤더 "캠페인"입니다. 개설 화면만 LNB 하단에 "이용 가이드" 링크가 보이는데 도착 화면이 없어 **숨깁니다**(D-6) |
| 서비스 카드 | "캠페인 등록" 섹션에 모집형·PICK형·라이브형·어필리에이터형 4장(PC 4열, TAB 2열, MO 1열)입니다. 하위 유형 배지(브랜드형·공구형 등)와 설명 3줄은 시안 문구 그대로입니다. 라이브형·어필리에이터형은 "추후 제공 예정이에요. 곧 만나요!" + 비활성 "준비중"이고 눌러도 아무 일이 없습니다(카드 선택·구독·데모·등록 모두 없음, REQ-4-0008·0009) |
| 구독 상태 | `entities/subscription`의 구독 목록으로 판단합니다(`getSubscribedTypes`, 해지 예정·결제 실패도 구독 중으로 보는 기존 기준). 구독 중이면 카드 상단 "이용 중" 뱃지(시안 3.0.2 추가), 1px 파란 링(선택하면 2px 링+흰 간격으로 바뀜), "캠페인 등록하기" 버튼(2026-11-27 시안, 누르면 카드를 누른 것과 같이 서비스를 선택해 상품 카드를 보임), 아니면 위에 "구독하기 >"(outline), 아래에 "데모 체험하기"(primary) 버튼입니다. 모집형·PICK형 구독은 따로 판단하고 둘 다 이용 중일 수 있습니다(REQ-4-0005). 구독 중일 때 "데모 체험하기"는 **PC 시안대로 숨깁니다**(REQ-4-0010·0022와 같음, TAB·MO 시안은 보임 → D-7). **구독이 만료되면 미구독과 똑같이** 보입니다(REQ-4-0020). 화면에 들어올 때마다 구독 목록을 다시 읽어(SWR 마운트 재조회) 구독하고 돌아오면 바로 반영합니다(REQ-4-0002·0012). 구독 목록을 못 불러오면 모두 미구독으로 보여 주지 않고 오류 안내를 띄웁니다 |
| 서비스 선택 | 구독 중인 카드를 누르거나 미구독 카드의 "데모 체험하기"를 누르면 그 카드가 선택(파란 테두리)되고 아래에 "캠페인 상품 선택" 섹션이 나옵니다. 사용자가 서비스를 직접 골랐을 때 이 섹션 제목이 화면 밖이면(주로 서비스 카드가 세로로 쌓이는 MO) 제목이 맨 위에 오도록 부드럽게 내려가고(모션 줄이기 설정이면 바로 이동), 제목이 이미 화면 안에 있으면 움직이지 않아 서비스를 바꿔 눌러도 화면이 다시 움직이지 않으며 `?service=`로 바로 열린 경우(새로고침·뒤로가기)에도 내리지 않습니다(사용자 결정 2026-11-25, 시안에 없는 동작). 선택은 `?service=recruit\|pick`입니다. 처음 들어오면 선택 없음이고 상품 섹션이 없습니다(`9853:935165`). LNB·현황의 "캠페인 등록하기"는 쿼리 없이 `/campaign/new`로 가므로 다시 들어오면 선택이 풀리고(REQ-4-0002 "재진입 시 서비스·데모 선택 초기화"), 새로고침·뒤로가기는 쿼리로 유지합니다. **미구독 카드는 "데모 체험하기" 버튼을 눌러야** 데모 상품 카드가 나오고(카드 영역을 눌러도 반응 없음, 사용자 결정 2026-11-25), 실제 등록 상품은 보이지 않습니다(REQ-4-0011). "이용 안내"("데모 체험은 무제한으로 이용 가능합니다." / "캠페인 등록은 해당 구독 상품을 구독해야 진행할 수 있습니다.")는 늘 맨 아래에 있습니다 |
| 상품 카드 | 선택한 서비스 이름(파랑) + "브랜드형"/"공구형" + 설명 4줄입니다. 설명은 시안(3.0.2) 문구 그대로이되 **"구매리뷰형" 표기만 뺍니다**(2026-11-13 스펙아웃, 사용자 결정 2026-11-13): "제품발송형, 매장방문형, 기자단형 진행", "원고 컨펌 부가서비스 선택 가능(건 당 5,000원)". 개정 명세서(REQ-4-0015~0018)는 서비스별 설명을 새로 정했는데(모집형 = 공개 모집·신청자 선정, PICK형 = 직접 탐색·제안, "원고컨펌") 시안은 PC가 PICK형 전용 문구("크리에이터 직접 탐색 및 크리에이터별 캠페인 제안" 등)이고 MO는 두 서비스가 같은 문구라, PC 기준으로 두고 D-8로 정정을 요청합니다. **구독 중 서비스**: 카드 전체가 버튼이고 아래에 "캠페인 등록하기" 버튼도 있어(2026-11-27 시안, 카드를 누른 것과 같음) 브랜드형은 `/campaign/register?type=<service>`, PICK형 공구형은 `/campaign/register?type=pick&product=group-buy`, 모집형 공구형은 준비 중 토스트입니다. **미구독 서비스**: 카드마다 "데모 캠페인 등록 >"이 있습니다. PICK형 브랜드형은 `/campaign/register?type=pick&demo=true`(데모 모드, 사용자 결정 2026-11-12), PICK형 공구형은 `?type=pick&product=group-buy&demo=true`(사용자 결정 2026-11-20), 모집형은 준비 중 토스트입니다(모집형 데모는 모집형 갱신 때, register P-28) |
| 구독하기 | `/mypage/subscribe`로 갑니다(REQ-4-0011·0012). 해당 상품을 미리 고른 상태로 열지는 않습니다(구독 화면에 그런 진입이 없음) |
| 데모 정책 | 데모 횟수는 제한이 없고 만들 때마다 따로 저장됩니다. 구독 전에 만든 데모는 **구독한 뒤에도 조회·이어 쓰기**가 됩니다(새 데모 생성만 막음). 데모를 지우면 현황과 이전 캠페인 불러오기 목록에서 빠집니다. 구독한 뒤 새 실제 캠페인에서 같은 서비스·상품 조합의 데모만 불러올 수 있습니다(REQ-4-0021~0024, 등록 화면 규칙은 [register](./register.md) §3 데모 모드) |
| 등록 진입 권한 | 로그인한 광고주만 들어옵니다. 비회원은 기존 세션 middleware가 로그인으로 보냅니다(REQ-4-0003). 이 앱은 광고주 계정 전용이라 명세 REQ-4-0004의 "크리에이터 모드"는 해당이 없습니다(PRD에 모드 개념 없음). 서버는 캠페인 생성·저장 때 구독을 검사하지 않고 결제 때만 검사하므로(API A-1·A-9), 미구독·만료 서비스의 실제 등록 진입은 이 화면(구독 상태)과 현황 "작성하기"(P-5)가 막습니다(REQ-4-0019·0020) |
| 구독 만료 뒤 등록 중 캠페인 | 만료된 서비스의 등록 중 실제 캠페인은 입력값을 보존하되 **수정 진입을 막습니다**(REQ-4-0020). 현황 "작성하기"를 누르면 그 서비스 구독을 확인해, 없으면 이동하지 않고 구독 안내 알럿(문구 §6, "취소" · "구독하기")을 띄웁니다(P-5). 데모 캠페인은 제외입니다 |
| Sub ID | 등록 마법사처럼 Sub ID는 개설에 들어올 수 없습니다(세션 middleware가 계정 설정으로 보냄) |

## 4. 배치

| 슬라이스 | 담는 것 |
|---|---|
| `pages/campaign-status` (신규) | `/campaign`. 탭·툴바·표/카드 목록·빈 상태·바로 가기 연결. 표와 카드는 이 화면에서만 쓰므로 페이지 안에 둡니다 |
| `pages/campaign-create` (신규) | `/campaign/new`. 서비스 카드·상품 카드·이용 안내. 구독 상태는 `entities/subscription`의 `useSubscriptions` |
| `features/delete-campaign` (신규) | 휴지통 → 확인 알럿 → 삭제 → 목록 캐시 갱신 → 토스트. 삭제 가능 여부(등록 중만)도 여기서 정합니다 |
| `entities/campaign` (확장) | 목록 조회·삭제 fetcher, 목록 스키마, 진행 단계 코드 `CAMPAIGN_STAGES`, 진행 단계 배지 `CampaignStageBadge`(등록 내역 등 다른 화면에서도 쓸 수 있게 entity UI로 둠) |
| `widgets/app-shell`·`pages/home` (수정) | LNB "캠페인" → `/campaign`, LNB "캠페인 등록하기" → `/campaign/new`, 홈 "캠페인 등록/운영" 카드 → `/campaign`. 모든 빌드에서 연결 |
| `shared/config`·`app/router` (수정) | `ROUTES.campaign`·`ROUTES.campaignCreate` 추가. 두 경로는 모든 빌드에서 실제 페이지. `MASTER_ONLY_PATHS`에 `/campaign/new` 추가(`/campaign`은 Sub ID 허용) |

- 탭·검색·필터 상태는 주소 쿼리가 원본이고 Zustand를 쓰지 않습니다. MO 필터 화면은 공통 `list-filter`가 `?panel=filter`로 소유합니다.
- 바로 가기 목적지는 진행 단계 하나로 정해지는 표(§3)라 페이지 `lib`의 순수 함수(진행 단계·Sub ID → 버튼 종류·경로)로 두고 테스트합니다.

## 5. 데이터 흐름의 예외

- **서버 API로 조회·삭제합니다.** `entities/campaign/api` fetcher가 서버 응답을 Zod로 검증합니다. 아래는 캠페인 등록 API 요구 명세의 목록 A-2·삭제 A-4와 현황용 프론트 요청 필드를 정리한 것입니다(§1).
  - **목록** `GET /v3/campaign`(API A-2): 탭은 `status`로 보냅니다. 전체 = 없음, 등록 중 = `DRAFT`, 승인 대기/반려 = `REVIEWING,REJECTED`, 진행 중 = `IN_PROGRESS`, 종료 = `ENDED`. 유형 필터는 `serviceType`(`PICK`·`RECRUIT`) + `productType`(`BRAND`·`GROUP_BUY`), 검색은 `keyword`(캠페인명·브랜드명, REQ-5-0005), 쪽은 `page`·`entrySize=15`. 응답은 `{list, count, currentPage, entrySize}`이고 항목은 `campaignIdx`·`campaignCode`·`serviceType`·`productType`·`status`·`name`·`brandName`·`campaignType`·`platform`·`createdDate`입니다. **현황에 더 필요해 요청한 필드**: `description`(부제, REQ-5-0011)·`thumbnailUrl`(5단계 메인 이미지)·`startDate`·`endDate`(승인 전은 희망 일정)·`demo`·`demoCompleted`. 정렬은 최초 등록일 최신순 + 고정 보조 기준(REQ-5-0013, 요청). 계정 전체 0건은 조건 없는 전체 조회의 `count=0`으로 판단합니다.
  - **삭제** `DELETE /v3/campaign/{campaignIdx}`(API A-4): 등록 중(`DRAFT`)만, 데모 포함. 아니면 `409 NOT_DELETABLE`(토스트 후 목록 다시 읽기), Sub ID는 `403`.
- **진행 단계는 서버 `status`로 정합니다.** 코드는 `DRAFT`·`REVIEWING`·`REJECTED`·`IN_PROGRESS`·`ENDED`이고(API 코드 표, 등록 상세와 같은 값) 화면 배지는 등록 중·승인 대기·승인 반려·진행 중·종료입니다. 진행 중·종료는 서버가 승인 여부와 종료일로 나눠 주므로 프론트가 날짜로 계산하지 않습니다. 모르는 코드가 오면 배지는 서버 값 그대로, 바로 가기는 등록 내역으로 둡니다. (전에 따로 받으려던 목록 전용 코드 `PENDING`과 `tab` 파라미터는 쓰지 않습니다.)
- **API에서 확인할 것**: 위 요청 필드(부제·썸네일·기간·데모)를 목록 응답에 넣어 주는지, 승인 전 기간을 구분하는 값이 필요한지(P-6). 해소: 종료 판정(서버 `status`, REQ-5-0029), 정렬(최초 등록일 최신순), Sub ID는 배정된 캠페인만 받음(API A-2 접근 규칙).
- **개발 확인**: 진행 중·종료 캠페인은 마법사로 만들 수 없어서, stage 서버에서 개발용 승인(`/test/approve`, 승인 완료 = 진행 중)으로 만들어 확인합니다.
- **목록 조회 훅은 하나입니다.** PC·TAB·MO 모두 `useInfinitePages`로 이어 읽어, 화면 폭이 바뀌어도 같은 캐시와 읽어 둔 목록을 그대로 씁니다. 계정 전체 0건 확인만 한 쪽을 읽는 SWR(`useCampaignPage`)입니다.
- **캐시 갱신**(사용자 결정 2026-11-27, PC·TAB도 이어 읽기로 바꾸며 같은 날 통일): 첫 쪽만 다시 읽으면 맨 위에 항목이 생긴 만큼 쪽 경계가 밀려 항목이 빠지고, 모두 다시 읽으면 돌아올 때마다 읽어 둔 쪽 수만큼 요청이 나가므로, 다시 보일 때 캐시를 그대로 보여 스크롤 위치를 되돌리고 이 앱에서 캠페인을 바꾼 요청이 성공했을 때만 그 뒤 처음 보일 때 바뀐 만큼 다시 읽습니다. **내용만 바뀜**(단계 저장·이전 캠페인 불러오기·데모 작성 완료: 정렬·탭·건수 그대로)이면 그 캠페인이 있는 쪽만(SWR "Revalidate Specific Pages"), **목록 구성이 바뀜**(생성·삭제·결제(승인 요청)·승인 요청 취소·재승인 요청·데모 전환)이면 읽어 둔 쪽을 모두 다시 읽습니다. 검색 중인 목록은 이름이 바뀌어 결과에서 빠질 수 있어 내용만 바뀌어도 모두 다시 읽습니다. 화면에서 직접 다시 읽으면(삭제 후 등) 그때까지의 변경은 반영된 것으로 봅니다. 관리자 승인·기간 종료·Sub ID 수정처럼 이 앱 밖의 변경은 새로고침해야 보입니다(알림을 신호로 쓰는 방식은 과하다고 보고 두지 않음). 삭제한 캠페인의 등록 초안·내역 캐시는 지웁니다.

## 7. 범위 밖

- 캠페인 진행 화면은 [progress](./progress.md)가 맡습니다(PICK형 브랜드형부터). 모집형·공구형 진행은 범위 밖이라 현황 바로 가기가 준비 중 토스트입니다.
- 모집형 데모 체험 등록(REQ-4-0021~0024, register P-28)과 공구형 등록(9·11번 탭). 개설 화면의 버튼·카드는 시안대로 보이되 준비 중 토스트입니다. PICK형 브랜드형 데모는 범위 안입니다(register §3 데모 모드).
- 명세에만 있고 시안에 진입점이 없는 것(6·7번 옛 탭): 상태 필터(6-0025·7-0024), 진행 중 캠페인 등록 정보 수정·취소(7-0018~0020), 승인 완료 알림(6-0023, 알림 25번 탭).
- 개설 "이용 가이드"(D-6 답 후), 라이브형·어플리에이터형.
- 실제 API 연동(API A-2·A-4가 나오면 fetcher만 바꿈), stage·prod 공개.

## 9. 검증

- `pnpm verify`. 라우트·`app-shell` LNB·세션 middleware를 바꾸므로 `pnpm build`도 돌립니다.
- 구현하는 변경에서 `docs/pages.md` 화면 표에 `/campaign`·`/campaign/new` 행을 추가하고 홈·LNB 진입 설명을 고칩니다(표는 구현된 화면만 담음).
- 화면 확인(PC 1440·TAB 768·MO 360, stage 서버에 붙인 개발 서버, 시안 대조, `?lng=en` 넘침 확인)
  1. LNB "캠페인"·홈 카드 → `/campaign` 전체 탭, LNB "캠페인 등록하기"·현황 "+ 캠페인 등록하기" → `/campaign/new`인지 봅니다. stage 빌드에서도 두 경로와 진입점이 열리는지 확인합니다.
  2. 탭마다 해당 진행 단계만 나오고(전체는 모두, 데모는 전체·등록 중), 탭을 바꾸면 처음부터 다시 읽고 검색어·유형이 유지되는지, 새로고침·뒤로가기에 탭·검색·유형이 유지되는지, 초기화 아이콘이 탭은 두고 검색어·유형만 비우는지, 캠페인명·브랜드명으로 검색되는지, 한 번에 15개씩 이어 읽고 최초 등록일 최신순인지 봅니다. 잘못된 `tab`은 전체 탭입니다.
  3. 배지 5종 색·문구, DEMO 태그, 상태별 바로 가기·아이콘(§3 표)과 이동 경로를 확인합니다. "작성하기"는 첫 미완 단계로(데모는 데모 모드로), 작성 완료 데모의 "작성하기"는 데모 안내가 있는 기본 정보로, "반려 사유"는 보완 요청 메시지가 보이는 등록 내역으로 열립니다. 구독이 만료된 서비스의 실제 등록 중 캠페인 "작성하기"는 구독 안내 알럿을 띄웁니다. "캠페인 관리"·"결과 확인"은 준비 중 토스트입니다.
  4. 등록 중 삭제(데모 포함): 알럿 → 삭제 → 목록에서 빠지고 토스트, 같은 캠페인의 작성 주소가 더 이상 열리지 않고 이전 캠페인 불러오기 목록에서도 빠지는지 봅니다. 승인 대기·반려·진행 중·종료에는 휴지통이 없고 문서 아이콘입니다.
  5. 빈 상태 세 가지(계정 0건은 "캠페인 등록하기" 버튼, 탭별 문구, 검색·필터 결과 없음은 버튼 없음), 불러오기 실패·이어 읽기 실패(다시 시도)를 봅니다.
  6. PC 표·TAB 2열 카드(아이콘이 바로 가기 오른쪽)·MO 1열 카드가 모두 이어 읽는지, MO "필터" 화면(`?panel=filter`, 초기화·적용하기, 뒤로가기로 닫힘), MO는 모든 탭에 "+ 캠페인 등록"이 있는지 봅니다. 화면 폭을 바꿔도 목록이 깨지지 않는지 봅니다.
  7. 등록 마법사에서 새로 만든 캠페인이 현황 등록 중 탭에 바로 나오고, 결제 후 승인 대기로, 개발용 전환 버튼으로 반려·승인 완료(진행 중)로 바뀌는지 봅니다.
  8. 개설: 구독 없음(서비스 카드만 + 이용 안내), 구독 중 서비스(PC는 "캠페인 등록하기"만, 카드 선택 → 상품 카드, 브랜드형 클릭 → `/campaign/register?type=`), 미구독 서비스("데모 체험하기"·카드 선택 → 상품 카드에 "데모 캠페인 등록" → PICK형 브랜드형은 데모 모드 등록 마법사, 모집형은 준비 중 토스트, "구독하기" → `/mypage/subscribe`), 공구형 → 준비 중 토스트, 라이브형·어플리에이터형 무반응, `?service=` 새로고침 유지, 구독 정보 실패 안내를 확인합니다.
  9. Sub ID: 현황은 버튼 3종(등록하기·작성하기·휴지통)이 숨고 등록 내역 이동은 되는지, `/campaign/new`는 계정 설정으로 보내지는지 확인합니다.
