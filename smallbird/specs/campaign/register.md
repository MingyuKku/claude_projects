## 1. 목적과 범위

- 구독 중인 광고주가 **브랜드형 캠페인을 8단계 마법사로 등록**하고, 빅버드 머니로 결제한 뒤 운영팀 승인 상태를 등록 내역(기본 정보) 화면에서 확인·대응합니다.
- 서비스 유형은 **PICK형 브랜드형**과 **모집형 브랜드형** 두 가지이고 한 마법사로 만듭니다. 차이는 §3 "서비스 유형별 차이"에만 있습니다.
- **API는 아직 없습니다.** 프론트가 백엔드에 줄 API 요구 명세를 따로 만들 예정이고(사용자, 2026-11-05), 그 전까지는 목 데이터로 동작합니다(§5).
- 진입 경로는 이번 범위가 아닙니다. LNB "캠페인 등록하기"와 홈 "캠페인 등록/운영" 카드는 지금처럼 비활성으로 두고 **캠페인 개설·현황 작업 때 연결**합니다. 이번에는 URL로 직접 들어와 확인합니다.

### 시나리오

1. `/campaign/register?type=pick|recruit`로 들어오면 서버가 **등록 중 캠페인을 만들고 캠페인 코드를 발급**합니다(REQ-10-0052). 주소를 `/campaign/register/:campaignId?step=campaign-info`로 바꿉니다(`replace`).
2. 1~8단계를 입력합니다. 사이드바로 어느 단계든 건너뛸 수 있고, 비어 있는 단계는 느낌표로 표시됩니다. 입력은 자동 저장되고(§3 저장), "임시저장"으로 직접 저장할 수도 있습니다. 나갔다가 같은 주소로 다시 오면 이어서 씁니다.
3. 8단계에서 빅버드 머니로 결제하면 결제 완료 알럿이 뜹니다. "확인"을 누르면 `/campaign/:campaignId`(승인 검토중)로 갑니다.
4. 승인 검토중에 "승인 요청 취소"를 누르면 결제 금액이 환불되고 캠페인이 등록 중으로 돌아가 다시 고칠 수 있습니다(고친 뒤 8단계에서 다시 결제). 반려되면 수정이 필요한 섹션과 반려 사유가 보입니다. 섹션 "수정"으로 해당 단계를 고친 뒤 "재승인 요청"을 보냅니다(최대 2회). 승인이 완료되면 조회만 합니다.

### 1단계 캠페인 정보

- 캠페인 코드는 서버 값 그대로 읽기 전용 텍스트입니다(형식 "PB…"/"CMP-…" 차이는 서버가 정함).
- 캠페인명(필수, 길이 제한 없음, P-11), 캠페인 유형(필수, 4개 중 1개), 브랜드명(필수)을 받습니다.
- 브랜드 선택 메뉴는 맨 위 "+ 브랜드 추가"에 등록된 브랜드 목록이 이어지고, 8개를 넘으면 메뉴 안에서 스크롤합니다(주석 원문).
- 날짜는 **고르기 전에는 1칸**(라벨 "캠페인 희망 시작 일자"*, 도움말 "종료 날짜는 자동으로 30일 후로 세팅됩니다.")이고, **고른 뒤에는 라벨이 "캠페인 기간"으로 바뀌며 시작일·종료일 2칸**으로 보입니다(사용자 확인: 시안의 두 모양은 선택 전·후 상태). 종료일은 시작일 + 30일로 정해지는 읽기 전용 값입니다.
- 캘린더는 **오늘 이전 날짜만 막습니다**(v2와 같음: v2는 오늘부터 선택, 구독 종료일·승인 기간을 반영하는 규칙 없음, 2026-11-05 v2 코드 확인). 요구명세서의 "구독 이용기간 종료일 이전 시작"(REQ-10-0016)은 v2에 없던 규칙이라 이번에는 적용하지 않습니다.
- **이전 캠페인 불러오기**
  - 검색어(캠페인명 또는 브랜드명)를 "검색" 버튼이나 Enter로 실행하고, 결과를 캠페인명·브랜드·유형·플랫폼·등록일로 보여 줍니다.
  - **1개만 선택**하고 다른 행을 고르면 앞 선택이 풀립니다. 헤더의 전체 선택 체크박스는 시안 오류라 그리지 않습니다(사용자 확인, REQ-8-0011).
  - "캠페인 불러오기"는 선택이 있을 때만 활성입니다. 누르면 고른 캠페인의 **1~6단계 입력값 전체**를 현재 캠페인에 복사하고(사용자 결정), 캠페인 코드는 지금 것을 유지합니다. 7단계 약관 동의와 결제는 복사하지 않습니다. 희망 시작일이 지난 날짜면 오늘로 맞춥니다(v2 동작). 현재 캠페인에 **입력한 값이 하나라도 있으면 덮어쓰기 확인 알럿**을 먼저 띄웁니다(사용자 결정, 문구 §6).
  - 0건과 검색 결과 없음은 시안이 없어 목록 영역을 비워 둡니다(P-9).
- **브랜드 추가**
  - 브랜드명(국문)*과 브랜드명(영문)*을 받고, 브랜드 이미지는 선택이며 올리지 않으면 기본 프로필을 씁니다.
  - "저장"은 국문·영문이 모두 입력됐을 때만 활성입니다(D-6). 저장하면 브랜드 목록을 다시 읽고 새 브랜드를 선택한 채 닫습니다.
  - 이미지는 미리보기와 Hover "×" 삭제가 있고, TAB·MO는 썸네일을 다시 누르면 파일을 다시 고릅니다(주석 `7555:393227`). 형식·용량은 5단계 메인 이미지와 같게 JPG·PNG 10MB로 둡니다(P-12).

### 3단계 인플루언서 조건

- 플랫폼*은 1개만 고릅니다. 인스타그램·블로그·페이스북·유튜브·틱톡·엑스(시안 순서와 표기)이고, 아이콘 토글입니다.
- 선호 성별*은 여성·남성·전체 중 1개입니다.
- 선호 연령대*는 10대~50대 이상에서 1개 이상, 포스팅 주제*는 뷰티·패션·푸드·여행·육아·라이프·건강·IT에서 1개 이상 고릅니다. 최대 개수 제한은 없습니다.
- 기존 `entities/platform`은 인플루언서 검색용(4개)이라 쓰지 않습니다. 캠페인 플랫폼 6개는 `entities/campaign`이 소유합니다. 아이콘만 `PlatformIcon`을 늘려 함께 씁니다(소비처 확인).

### 4단계 부가서비스

- 위 안내 박스는 "부가서비스는 선택사항입니다."이고, 아무것도 고르지 않아도 "다음"을 통과합니다.
- 카드를 누르면 선택이 켜지고 꺼집니다. 선택된 카드 모양은 시안에 없어 토글과 같은 `Pressed` 스타일로 둡니다(D-2).
- 가격 배지는 시안 원문을 그대로 쓰고(AI 포스팅 가이드 "10,000원", AI 원고컨펌·AI 영수증 리뷰 "모집 인플루언서 당 5,000원"), **PICK형은 부가서비스가 AI 포스팅 가이드 하나뿐입니다**(사용자 결정, 요구명세서 REQ-10-0020·0021·0022·0075의 PICK형 AI 원고컨펌과 시안 `7555:335960`·`7555:334661`은 수정 필요). 청구액은 8단계에서 계산해 보여 줍니다.

### 5단계 캠페인 소개서 / 모집동의서

- 작성 방식 카드 "AI … 작성" / "직접 작성하기" 중 하나를 고릅니다. 방식을 바꿔도 입력값은 지우지 않습니다.
- **AI**: 상품/서비스 URL*을 넣고 "AI 생성"을 누릅니다. 생성 중에는 안내(`Message Alert`, 취소 없음)를 띄우되 **다른 단계로 이동해 계속 작업할 수 있습니다**(사용자 결정, 5분 동안 기다리지 않게). 생성 중에는 5단계 입력칸만 잠그고, 작업 id를 초안에 남겨 새로고침해도 이어서 기다립니다. 5단계가 아닌 곳에 있을 때 끝나면 토스트로 알리고 사이드바 5단계에 "생성 중"·완료 표시를 보입니다(시안 대기). 끝나면 별도 카드 "AI 생성"에 메인 이미지·상세 미디어·설명·유의사항·해시태그를 채우고, 사용자가 고칠 수 있습니다. "다시 생성하기"는 확인 없이 덮어씁니다(P-13). 생성 실패는 토스트이고 기존 입력은 그대로 둡니다. 생성 결과가 있어야 "다음" 검사를 통과합니다.
- 공통 필드
  - 메인 이미지*: 1장, JPG·PNG 10MB, 권장 1200×630
  - 상품 상세 이미지/동영상*: 1~5개, 드래그 앤 드롭으로 올리고 Hover하면 순서 핸들과 "×"가 보임, 동영상 썸네일에는 재생 아이콘 + 길이 표시
  - 캠페인 설명*, 유의사항*
  - 필수 해시태그(키워드)*: Enter로 칩 추가, 칩 "×"로 삭제, 1개 이상, 같은 값은 넣지 않음
- **AI 시안 프레임으로 통일합니다**(사용자 결정, D-7): 캠페인 설명·유의사항 상한은 직접 작성도 AI 결과와 같은 **1000자**, 필드 구성·순서도 AI 결과 프레임(`7555:335869`)과 같습니다. 요구명세서 REQ-10-0027·0028의 "직접 작성 300자"와 달라 명세서 정정이 필요합니다.
- 파일은 고르는 즉시 서버에 올리고 받은 URL·ID로 저장합니다(목은 로컬 미리보기 URL). 동영상 형식·용량·길이는 P-12입니다.
- **미리보기**: 내용이 없으면 비활성이고, 미리보기 화면은 시안이 없어 버튼만 둡니다(동작 없음, D-8).
- MO 직접 작성에 "유의사항"이 없는 시안(`7555:430792`)도 AI 프레임에 맞춰 PC·TAB과 같은 필드·순서로 둡니다. 해시태그는 "필수 해시태그(키워드)" 1개이고, 등록 내역의 "(제목)"·"(본문)" 2종 표시는 디자인팀에 정정을 요청합니다.

### 6단계 진행 조건

- 포스팅 유지기간*: 1·3·6·12개월·직접 입력이고, 직접 입력이면 "개월" 정수 1 이상을 받습니다(상한 P-11).
- 2차 저작권 사용 여부*: 사용 / 미사용
- **PICK형 구매리뷰형은 입력할 것이 없습니다**(사용자 결정: PICK형은 리워드가 없음). 화면은 그대로 나와야 해서 안내만 보여 주고(시안 대기, D-9) "다음"은 바로 통과합니다. 요구명세서 REQ-10-0061·0063(구매리뷰형 리워드)과 시안 `7803:325894`·`7803:375714`는 이 결정과 달라 정정이 필요합니다.
- 모집형 구매리뷰형은 유지기간·2차 저작권 없이 모집 인원*과 리워드*만 받습니다(`7816:293767`).
- 리워드*는 **모집형 제품발송형·구매리뷰형에만** 있습니다(사용자 결정: PICK형은 리워드 없음, 기자단형·매장방문형도 리워드 없음. 요구명세서 REQ-8-0017·0020·0068이 이 두 유형만 말하고, "상품 금액"도 이 두 유형에만 있어 맞습니다). 원 단위 1원 이상이고 **상한은 상품 금액**입니다: 제품발송형은 협찬제품 금액(제품 1개당), 구매리뷰형은 구매제품 금액(2단계 신규 입력)입니다. 도움말은 "최대 {금액}원까지 가능하며 입력한 리워드 금액은 캠페인 종료 후 최종 정산 금액에 반영됩니다."이고, 시안의 "최대 50,000원"은 고정값이라 따르지 않으며 모집형 6단계 일반 시안(`7816:292237`)이 기자단형·매장방문형에도 리워드를 그린 것은 정정을 요청합니다.
- 리워드는 **인플루언서 1인당 금액**입니다(REQ-8-0017).
- 진행 인원*·모집 인원*(모집형): 숫자 스테퍼(− n 명 +)이고 1명 이상입니다(제한 없음, 사용자 결정).

### 7단계 캠페인 정책 동의

- "약관 전체 동의"는 필수 4개(서비스 이용약관·개인정보 처리방침·캠페인 운영 정책·리워드 및 결제 관련 정책)를 한꺼번에 켜고 끕니다. 4개가 모두 켜지면 전체도 켜집니다.
- 항목의 ">"를 누르면 약관 전문을 엽니다(PC·TAB 다이얼로그, MO 전체 화면). "동의하기"는 그 항목을 켜고 닫고, "취소"는 닫기만 합니다.
- 전문은 `entities/terms`가 갖습니다. 서비스 이용약관·개인정보 처리방침은 있는 본문을 쓰고, **캠페인 운영 정책·리워드 및 결제 관련 정책도 프론트가 관리합니다**(사용자 결정). 두 정책은 원문이 없어 원문을 받을 때까지 ">"를 숨기고 체크만 받습니다(P-14).
- 4개 모두 동의해야 "다음" 검사를 통과합니다.

### 8단계 결제

- 카드 4개로 구성합니다: PC는 2×2이고, TAB·MO는 캠페인 요약 → 결제 수단 → 결제 요약 → 약관 동의 순서로 세로입니다.
- **금액은 프론트가 초안 값으로 계산합니다**(사용자 결정, 규칙이 단순함, REQ-8-0058 "실제 설정된 내역 기준"). `calculatePayment`가 한 곳에서 계산하고 화면은 그 결과만 씁니다. 단가·계산식: AI 포스팅 가이드 10,000원 정액, AI 원고컨펌·AI 영수증 리뷰(모집형만) 인원당 5,000원 × 진행 인원, 리워드(모집형 제품발송형·구매리뷰형만) = 1인당 리워드 × 진행 인원, 총 결제 금액 = 부가서비스 합 + 리워드 총액(시안 예시 수치와 맞음). 결제 요약의 부가서비스 행은 고른 것만, 리워드 행은 모집형만 보여 줍니다. PICK형은 부가서비스가 AI 포스팅 가이드 하나뿐이라 인원 계산이 필요 없고, 부가서비스를 고르지 않으면 총액이 0원입니다. 0원이어도 "결제하기"가 승인 요청 역할을 합니다(잔액 검사 생략, P-2). 돈이 오가므로 서버는 결제 요청의 `expectedTotalAmount`를 다시 계산해 다르면 거절하고, 프론트는 이때 `AMOUNT_CHANGED` 안내를 보입니다. 사용자가 앞 단계를 채우지 않고 8단계에 와도 있는 값으로 계산해 보여 줍니다.
- 결제 수단은 "빅버드 머니"(라디오 선택 고정 + "필수" 배지)이고, 보유 빅버드 머니는 헤더 P와 같은 잔액 SWR 키를 씁니다.
- **충전 영역**(충전 금액 입력·빠른 금액·"충전하기")은 시안대로 둡니다(사용자 결정). "충전하기"를 누르면 마이페이지 빅버드 머니 충전과 같이 약관 팝업 → 충전 요청(이니시스 무통장 입금) 순으로 갑니다. 금액 규칙·빠른 금액·안내 문구는 [money.md](../mypage/money.md)를 따르고(시안의 "최소 1,000원"·1/3/5/10만 원은 옛 값), 결제창 복귀 주소는 `/campaign/register/:id?step=payment`로 보내 접수 알럿("충전 요청 접수", 마이페이지 문구)을 띄웁니다. **무통장 입금은 입금이 확인돼야 잔액이 늘어서, 요청 직후에는 여전히 잔액 부족일 수 있습니다.** 시안의 즉시 "충전 완료" 알럿은 만들지 않습니다. 충전 UI는 `features/charge-bigbird-money`의 것을 쓰는데 feature끼리는 서로 가져올 수 없어서, 마법사는 `chargeSlot`을 받고 페이지가 채웁니다(§4).
- 약관 동의 카드는 7단계와 **같은 값**을 보여 주고 여기서 고쳐도 7단계에 반영합니다.
- "결제하기"를 누르면 다음 순서로 처리합니다.
  1. 모든 단계를 검사합니다. 비어 있는 단계(약관 미동의 포함)가 있으면 필수 항목 미입력 알럿을 띄우고 확인하면 첫 미완 단계로 보냅니다.
  2. 총액이 0원보다 크고 잔액이 총액보다 적으면 "결제 금액 부족" 알럿을 띄웁니다.
  3. 결제를 요청하고, 성공하면 "결제 완료" 알럿을 띄웁니다. 완료 알럿은 "확인"만 두고(빅버드 머니 스펙과 같은 규칙), "확인"을 누르면 `/campaign/:campaignId`로 `replace`합니다.
  4. 실패하면 토스트를 띄웁니다.
- **결제 완료가 곧 승인 요청**입니다(시안·REQ-8-0039, P-15). 별도 "승인 요청" 버튼은 없습니다.

### 등록 내역 (기본 정보)

- 제목은 "기본 정보"이고, 상태 배너와 섹션 카드 8개(번호 배지 + 섹션명 + 라벨·값 2열, MO도 2열)로 구성합니다. 섹션의 표시 항목·배지 문구는 캐시 문서 원문을 따릅니다.
- 승인 상태가 정하는 것은 배너·버튼·섹션 "수정"입니다. 상태 값은 서버 코드로 받습니다(§6).

| 상태 | 배너 | 배너 버튼 | 섹션 "수정" | 하단 |
|---|---|---|---|---|
| 승인 검토중 | info "현재 캠페인은 승인 검토중입니다." | 승인 요청 취소 → 확인 알럿(Destructive) → 환불 + 등록 중으로 전환, 작성 화면(8단계)으로 이동 | 없음 | 없음 |
| 반려 | 경고 "수정이 필요한 항목이 있습니다." | — | **반려된 섹션만**("수정 필요" 빨간 배지 + 진한 테두리 + 섹션 아래 회색 사유 박스) | 재승인 요청 |
| 재승인 검토중 | info "…재승인 검토중입니다. … (최대 2회까지 가능)" | 승인 요청 취소 | 없음 | 없음 |
| 승인 완료 | check "승인이 완료된 캠페인입니다." | — | 없음 | 없음 |

- 반려 사유는 **섹션 단위**로 서버에서 받습니다(필드 단위 하이라이트 없음).
- **승인 요청 취소(사용자 결정, 2026-11-05)**: 확인 알럿 "승인 요청 취소하기"를 누르면 **결제한 금액이 환불**(서버, 빅버드 머니에 반영)되고 캠페인이 **등록 중 상태로 돌아갑니다**. 프론트는 작성 화면(`step=payment`)으로 보내고, 사용자는 어느 단계든(부가서비스·인원·리워드 포함) 고친 뒤 8단계에서 다시 결제합니다. 그래서 시안의 "취소 후 수정 가능" 화면(섹션 "수정" 1~6번 + "재승인 요청", `7555:335263`·`7555:334268`)은 만들지 않습니다(디자인 정리 요청). 알럿 본문은 환불을 알리도록 §6 문구로 바꿉니다. 재승인 검토중의 취소도 같습니다.
- **반려 후 수정은 아직 정해지지 않았습니다**(P-19). 답 전에는 결제가 유지된다고 보고, 반려된 섹션의 "수정"으로 `/campaign/register/:campaignId?step=<slug>`에 들어가 고친 뒤 "재승인 요청"을 보냅니다(REQ-10-0076). 이때 금액에 영향을 주는 값(4단계, 6단계 인원·리워드)과 7·8단계는 잠그고, 사이드바 맨 위에 "기본정보"가 붙으며, 고친 단계의 "다음"은 저장한 뒤 등록 내역으로 돌아갑니다.
- "재승인 요청" 알럿(`7555:336027`)은 "확인"만 두고, 확인하면 재승인 검토중으로 다시 읽습니다. 재승인 횟수를 넘긴 요청은 서버가 거절하며 토스트로 알립니다(P-19).
- 시안의 하단 "임시저장"(반려)과 TAB·MO의 "이전·다음"은 이 화면에서 저장·이동할 입력이 없어 그리지 않고 PC 기준을 따릅니다(사용자 결정, D-10).
- Sub ID는 **본인에게 할당된 캠페인이면 이 화면을 볼 수 있습니다**(사용자 결정). 할당 여부는 서버가 정하고 아니면 403(홈으로)입니다. 취소·재승인·수정 버튼을 Sub ID에게 보여 줄지는 P-20이고, 답 전에는 조회만 되게 버튼을 숨깁니다.

```ts
type StepSlug = "campaign-info" | "product" | "influencer" | "add-ons" | "intro" | "conditions" | "policy" | "payment";
interface CampaignStepDefinition {
  slug: StepSlug;
  titleKey: string;            // 사이드바·단계 제목·MO 서브 헤더
  schema: ZodType;             // "다음" 검사 (서비스·캠페인 유형을 받아 만드는 함수일 수 있음)
  Step: ComponentType;         // store에서 값을 읽고 씀

```

- 이전 캠페인 불러오기·브랜드 추가·AI 생성은 지금 이 마법사에서만 쓰여 `register-campaign` 안에 둡니다. 다른 화면(예: 브랜드 관리)이 생기면 그때 feature로 뺍니다.
- `widgets/app-shell` 변경(사용자 확인): **`AppShell`에는 모드를 더하지 않고** 작업 전용 셸 `FocusShell`을 새로 둡니다. `AppShell` 안의 헤더 오른쪽 묶음(포인트·알림·프로필·로그아웃)만 `ShellHeaderActions`로 뽑아 두 셸이 같이 쓰고(동작 변경 없음, 기존 테스트로 확인), `shared/components/app-header`의 `AppHeader`에 메뉴 버튼 대신 뒤로가기("<")를 넣는 선택 prop을 더합니다(소비처 확인). 사이드바가 마법사 store를 읽어서 페이지가 `CampaignRegisterProvider`로 `FocusShell`과 본문을 함께 감쌉니다. MO 단계 드로어와 서브 헤더는 마법사가 직접 그립니다.
- 라우트는 로그인 필요(`requireSessionRoute`)이고, **Sub ID는 캠페인을 만들 수 없습니다**(사용자 결정). `session-middleware`의 `MASTER_ONLY_PATHS`가 경로를 정확히 비교하므로, `/campaign/register`와 `/campaign/register/:campaignId`를 막으려면 접두사 비교로 바꿔야 합니다(소비처 확인). Sub ID는 `ROUTES.mypageAccount`로 보냅니다. 등록 내역(`/campaign/:campaignId`) 조회는 캠페인 현황 작업에서 정합니다.
- `chargeSlot`: `features/charge-bigbird-money`가 인라인 충전 입력(금액·빠른 금액·"충전하기")과 약관 팝업·요청을 내보내고(`ChargeInline({ returnPath })`, 결제창 복귀 주소를 받도록 `buildChargePaths`를 넓힘), `pages/campaign-register`가 이를 마법사에 꽂습니다.

## 5. 데이터 흐름의 예외

- **API 없음 → 목.** `features/register-campaign/api`와 `entities/*/api`의 fetcher가 플래그를 보고 목 모듈로 응답합니다. 목도 응답을 Zod 스키마로 검증하고, 스키마는 백엔드에 줄 API 요구 명세의 초안 역할을 합니다. API가 나오면 fetcher만 바꿉니다. 목 저장소는 메모리 + `sessionStorage`(새로고침해도 이어 쓰기 확인용)입니다.
- 목이 필요한 동작
  - 초안 생성·조회·저장
  - 브랜드 목록·추가
  - 이전 캠페인 검색·불러오기
  - 파일 업로드
  - AI 생성(지연 3초)
  - 구매처 URL 확인
  - 결제 미리보기·결제
  - 등록 내역 조회
  - 승인 요청 취소·재승인
  - 개발용 상태 전환: 반려·승인 완료로 바꾸는 버튼. `import.meta.env.DEV`일 때만 보임
- **마법사 store가 작성 중 초안을 소유합니다.** 이것은 기본 원칙("서버 데이터를 Zustand에 복사하지 않음")의 예외입니다.
  - 진입할 때 서버 초안(SWR)으로 **한 번만** 채우고, 그 뒤 원본은 store입니다.
  - 저장 응답은 SWR 캐시만 갱신하고 store를 다시 채우지 않습니다. 입력 중인 값이 저장 응답으로 되돌아가지 않게 하기 위해서입니다.
  - store는 `features/join`처럼 Provider 안 context store입니다. 캠페인마다 새로 만들고, 화면을 떠나면 버립니다.
- 저장은 전체 초안 덮어쓰기로 가정합니다(요구 명세에서 확정). 가 본 단계 목록(`visitedSteps`)과 진행 중인 AI 생성 작업 id도 초안에 함께 저장해서, 다시 들어왔을 때 사이드바 상태와 대기를 복원합니다. 완료·경고 표시는 저장하지 않고 초안 값에서 계산합니다.
- 등록 내역·잔액은 store가 아니라 SWR로 읽습니다. 결제 금액은 서버에서 읽지 않고 초안 값으로 계산합니다(§3 8단계).

주소 검색은 Daum(카카오) 우편번호(P-1), PICK형 부가서비스는 AI 포스팅 가이드 하나(P-2), 리워드는 모집형 제품발송형·구매리뷰형만이고 상한은 상품 금액(P-3), 승인 요청 취소 = 환불 + 등록 중(P-8), 이탈 확인 알럿 없음(P-17), Sub ID는 할당받은 캠페인의 내역을 볼 수 있음(P-18), 5단계 문구는 모집동의서로 통일(D-5), 추천 문구 확정(V-1), 빌드 변수·CI 변경 보류하고 목은 개발 서버에서만(V-2), 별도 셸 `FocusShell`(V-3). 앞선 해소 항목은 팀 전달 문서의 "답변 받은 것" 표에 있습니다.

## 9. 검증

- `pnpm verify`. `AppShell`·`session-middleware`·라우트를 바꾸므로 `pnpm build`도 돌립니다.
- 화면 확인(PC 1440·TAB 768·MO 360, 개발 서버 목, 시안 대조, `?lng=en` 넘침 확인)
  1. `/campaign/register?type=pick`으로 들어오면 `/campaign/register/:id?step=campaign-info`로 교체되고 캠페인 코드가 보입니다. `type=recruit`면 5단계 이름이 "모집동의서 작성"입니다. 잘못된 `type`은 not-found입니다.
  2. 사이드바의 현재·완료·흐림·미완 경고(느낌표) 표시를 확인하고 어느 단계로든 이동되는지 봅니다. MO는 "≡" 드로어·서브 헤더 "임시저장"·하단 버튼(1단계 "다음"만)을 봅니다. 새로고침하면 같은 단계·입력값·가 본 단계 표시로 돌아옵니다.
  3. 필수값이 빠진 채 "다음"을 누르면 알럿이 뜨고 단계가 그대로입니다. 입력 3초 뒤 자동 저장, 계속 입력하면 30초마다 저장, 단계 이동 시 즉시 저장, "임시저장" 토스트를 확인합니다.
  4. 1단계: 브랜드 메뉴(8개 넘으면 스크롤)를 확인합니다. 브랜드 추가는 저장 활성 조건, 저장 후 선택 상태, PC 드로어 / TAB·MO 서브 화면, 뒤로가기로 닫힘을 봅니다. 캘린더는 PC 팝오버 / MO 바텀시트이고 오늘 이전 날짜가 비활성이며, 날짜를 고르면 라벨이 "캠페인 기간"(시작일·자동 종료일)으로 바뀝니다. 이전 캠페인 불러오기는 검색, 1개 선택(전체 선택 체크박스 없음), 입력한 값이 있을 때 덮어쓰기 알럿, 불러온 값 반영을 봅니다. 유형을 바꾸면 입력한 값이 있을 때 확인 알럿이 뜨고 2단계와 6단계 유형 전용 값이 지워집니다.
  5. 2단계: 유형은 읽기 전용이고 유형별 필드, 회수 있음·대여 상품 펼침, 금액 100만원 미만이면 대여 비활성이고 금액을 내리면 일반으로 되돌아감, 구매처 URL 확인 오류·정상과 URL 수정 시 초기화, 모집형 구매리뷰형의 구매제품 금액, 기자단형 바로 통과를 확인합니다. 주소 검색은 Daum 우편번호 팝업에서 고른 주소가 읽기 전용 주소 칸에 들어가고 상세 주소만 직접 입력되는지, 스크립트 로드 실패 시 토스트가 뜨는지 봅니다(테스트는 래퍼를 모킹).
  6. 3·4단계: 단일·복수 선택, 선택 스타일이 포커스와 구분됨, 4단계는 PICK형 AI 포스팅 가이드 카드 1개 / 모집형 3개(원고컨펌·영수증 리뷰 포함), 부가서비스 없이 통과를 확인합니다.
  7. 5단계: AI 생성 중 안내가 뜨고 다른 단계로 이동해 작업할 수 있는지(5단계 입력칸만 잠김), 새로고침해도 이어서 기다리는지, 끝나면 토스트와 결과 채움, 다시 생성, 실패 토스트를 봅니다. 직접 작성은 AI 결과와 같은 필드 순서이고, 업로드(형식·용량·5개), 드래그, 삭제, 해시태그 Enter·중복·삭제, 설명·유의사항 글자 수 카운터와 1000자 상한(300자는 2단계의 방문 혜택·구매 안내만), 미리보기 비활성/활성을 봅니다.
  8. 6단계: 직접 입력 개월, PICK형 구매리뷰형은 입력 없는 안내 화면, 모집형 구매리뷰형은 모집 인원 + 리워드, 모집형 제품발송형은 진행 인원 + 유지기간·2차 저작권 + 리워드, 기자단형·매장방문형은 리워드 없음을 확인합니다. 리워드 상한이 제품발송형은 협찬제품 금액, 구매리뷰형은 구매제품 금액이고 도움말에 그 금액이 들어가는지 봅니다.
  9. 7단계: 전체 동의 연동, 약관 전문(PC·TAB 다이얼로그 / MO 전체 화면) "동의하기"로 체크, 운영·리워드 정책은 ">" 없음을 확인합니다.
  10. 8단계: 계산한 금액(부가서비스 합·모집형 리워드 행·총액)이 맞는지, 부가서비스를 고르지 않은 PICK형(0원)도 "결제하기"가 승인 요청이 되는지, 앞 단계를 비운 채 들어와도 계산되는지, 비어 있는 단계가 있을 때 "결제하기" 알럿과 첫 미완 단계 이동, 잔액 부족 알럿, 결제 완료 → `/campaign/:id` 승인 검토중, "충전하기" → 약관 팝업 → 충전 요청 → 복귀 시 접수 알럿(`step=payment`)을 확인합니다. 사이드바에서 2단계 → 6단계로 건너뛰면 3~5단계(4단계 제외)에 느낌표가 뜨는지, Sub ID는 두 경로에 들어올 수 없는지 확인합니다.
  11. 등록 내역: 상태 4종(승인 검토중·반려·재승인 검토중·승인 완료, 개발용 전환 버튼)마다 배너·버튼·섹션 "수정"을 봅니다. 승인 요청 취소 알럿(환불 안내 문구) → 환불 + 등록 중 → 작성 화면 `step=payment`로 이동해 다시 결제할 수 있는지, 반려 섹션 "수정" → 해당 단계(수정 모드: 사이드바 "기본정보", 금액에 영향 주는 값과 7·8단계 잠금, 어느 단계든 "다음"은 저장한 뒤 내역으로 복귀), 재승인 요청 알럿 → 재승인 검토중, 반려 섹션 배지·사유를 확인합니다. 결제 전 캠페인을 내역 주소로 열면 작성으로, 승인 요청 이후 캠페인을 작성 주소로 열면 내역으로 보내지는지, 할당된 Sub ID는 내역을 볼 수 있고 버튼이 숨는지 봅니다.
  12. stage·prod 빌드에서 두 경로가 준비 중 화면인지 확인합니다.
