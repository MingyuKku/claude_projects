### 시나리오

1. `/campaign/register?type=pick|recruit`로 들어오면 서버가 **등록 중 캠페인을 만들고 캠페인 코드를 발급**합니다(REQ-10-0002, 중복 요청으로 두 개가 생기지 않게 서버가 막음). 주소를 `/campaign/register/:campaignId?step=campaign-info`로 바꿉니다(`replace`).
2. 1단계 필수값을 채우고 "다음"을 누르면 2~8단계가 열립니다. 그 뒤에는 사이드바·이전·다음으로 어느 단계든 오가며 입력하고, 입력은 단계를 옮길 때와 "임시저장"을 누를 때 저장됩니다(§3 저장). 나갔다가 같은 주소로 다시 오면 이어서 씁니다.
3. 8단계에서 "결제하기"를 누르면 모든 단계를 검사하고, 빅버드 머니로 결제하면 결제 완료 알럿이 뜹니다. "확인"을 누르면 `/campaign/:campaignId`(승인 대기)로 갑니다.
4. 승인 대기나 승인 반려 상태에서 "승인 요청 취소"를 누르면 결제 금액이 전액 환불되고 캠페인이 등록 중으로 돌아가 다시 고칠 수 있습니다(고친 뒤 8단계에서 다시 결제). 반려되면 운영팀의 보완 요청 메시지가 보이고, 등록 정보를 고친 뒤 "재승인 요청"을 보냅니다(추가 결제 없음). 승인이 완료되면 캠페인은 진행 중으로 넘어가고 등록 내역은 조회만 합니다.
5. PICK형 미구독 광고주는 개설 화면에서 데모 캠페인을 만들어 같은 마법사로 씁니다. 8단계 "등록 정보 보기"로 작성을 완료하면 조회만 되고, 구독한 뒤 같은 캠페인을 실제 캠페인으로 전환합니다(§3 데모 모드).

## 3. 확정 결정

### 공통

| 항목 | 결정 |
|---|---|
| 경로 | 신규 `/campaign/register?type=pick\|recruit`(만든 뒤 교체) → 작성 `/campaign/register/:campaignId?step=<slug>` → 등록 내역 `/campaign/:campaignId`(사용자 결정, 등록·내역 경로 분리). `step` slug는 `campaign-info`·`product`·`influencer`·`add-ons`·`intro`·`conditions`·`policy`·`payment`이고, 없거나 잘못된 값이면 "아직 완료하지 않은 첫 단계"로 엽니다. 숫자가 아니라 slug를 쓰는 이유는 공구형 9단계가 추가돼도 주소가 바뀌지 않게 하기 위해서입니다. `type`이 없거나 잘못되면 not-found입니다. 데모는 `?type=pick&demo=true`로 만들고(§3 데모 모드), 만든 뒤 주소는 실제 캠페인과 같습니다 |
| 상태별 진입 | 작성 경로에 승인 요청 이후 상태(승인 대기·승인 반려·진행 중)인 캠페인이 오면 `/campaign/:campaignId`로 보냅니다. 단, 반려 상태에서 "수정"으로 온 경우는 예외입니다(§3 등록 내역). 승인 요청을 취소하면 등록 중 상태가 되어 작성 경로로 열립니다. 반대로 등록 내역에 등록 중(결제 전) 캠페인이 오면 작성 경로로 보냅니다. 단, **작성 완료한 데모 캠페인**은 반대로 작성 경로에서 기본 정보로 보내고 기본 정보에서 조회합니다(§3 데모 모드) |

PC는 오른쪽 드로어(딤)이고, 약관은 PC·TAB 가운데 다이얼로그입니다. - 날짜는 **고르기 전에는 1칸**(라벨 "캠페인 희망 시작 일자"*, 도움말 "종료 날짜는 자동으로 30일 후로 세팅됩니다.")이고, **고른 뒤에는 라벨이 "캠페인 기간"으로 바뀌며 시작일·종료일 2칸**으로 보입니다(사용자 확인: 시안의 두 모양은 선택 전·후 상태). 종료일은 시작일 + 30일로 정해지는 읽기 전용 값입니다.
- 캘린더는 **오늘 이전 날짜만 막습니다**(v2와 같음: v2는 오늘부터 선택, 구독 종료일·승인 기간을 반영하는 규칙 없음, 2026-11-05 v2 코드 확인). 개정 명세서에는 희망 시작일 제한 규칙이 없습니다(옛 "구독 이용기간 종료일 이전 시작"은 "구독 기간 안에 매칭 완료"(REQ-10-0100)로 바뀌어 등록 단계와 무관).
- 희망 시작일·종료일은 **예정값**입니다. 실제 시작일은 운영 승인 시점에 정해지고 종료일은 그로부터 30일입니다(REQ-10-0024·0099). 등록 내역의 "진행 기간"은 서버가 주는 값을 그대로 보여 줍니다.
- **이전 캠페인 불러오기**
  - 검색어(캠페인명 또는 브랜드명, 시안 placeholder "캠페인명 또는 브랜드명을 검색해 주세요.")를 "검색" 버튼이나 Enter로 실행하고, 결과를 캠페인명·브랜드·유형·플랫폼·등록일로 보여 줍니다(REQ-10-0025의 "캠페인명만 검색"·"진행 상태" 열은 시안을 따라 넣지 않음). 목록 끝에 닿으면 다음을 이어 불러옵니다(무한 스크롤, 3.0.3).
  - 대상은 **같은 서비스 유형·상품(PICK형 브랜드형)의 캠페인**이고, 등록 중(임시저장)·승인 요청 취소·반려된 캠페인과 데모로 작성한 캠페인도 포함합니다(REQ-10-0025). 대상 거르기는 서버가 합니다.
  - **1개만 선택**하고 다른 행을 고르면 앞 선택이 풀립니다. 헤더 전체 선택 체크박스는 없습니다(3.0.3 시안에서 빠짐).
  - "캠페인 불러오기"는 선택이 있을 때만 활성입니다. 누르면 고른 캠페인의 **1~6단계 입력값 전체**(부가서비스 선택·업로드 자료 포함)를 현재 캠페인에 복사하고, 캠페인 코드와 등록 중 상태는 지금 것을 유지합니다. 7단계 약관 동의·동의 이력, 결제, 승인 이력은 복사하지 않습니다(REQ-10-0027). **복사는 서버가 합니다**(copy API): 원본 브랜드가 지금 계정에 없으면 브랜드는 비웁니다(REQ-10-0028). 원본이 구매리뷰형 캠페인(v2 등)이면 캠페인 유형과 2·6단계 유형 전용 값은 가져오지 않습니다(스펙아웃). 프론트는 복사 뒤 상세를 다시 읽어 초안을 채웁니다. 복사된 희망 시작일이 지난 날짜면 프론트가 오늘로 맞춥니다(v2 동작). 현재 캠페인에 **입력한 값이 하나라도 있으면 덮어쓰기 확인 알럿**을 먼저 띄웁니다(사용자 결정, 시안 3.0.5 `13320:133198` 문구 §6). 시안 캡션 "캠페인 불러오기 클릭 시 알럿 호출"은 늘 띄우는 것으로도 읽혀 확인 중입니다(P-33).
  - 빈 상태(시안 3.0.3, 둘 다 "캠페인 불러오기" 비활성): 검색 결과 없음 `13320:115789` 돋보기 아이콘 + "‘{검색어}’에 대한 검색 결과가 없습니다.", 대상 캠페인 없음 `13320:115800` "등록된 캠페인이 없습니다."
- **브랜드 관리**(3.0.5, 전 "브랜드 추가" 드로어를 대체, REQ-10-0018~0020)
  - 목록 `13320:115433`: 제목 "브랜드 관리", 소제목 "등록 브랜드" + 개수 "N개", 행마다 브랜드명(길면 말줄임) + "삭제" 버튼, 목록은 세로 스크롤, 하단 고정 "+ 브랜드 추가". 행은 PC에서 Hover 배경이고 TAB·MO는 눌림(Selected) 모양만 있습니다(주석 원문). 행을 눌러 브랜드를 고르는 동작은 시안에 없어 만들지 않습니다(브랜드 선택은 1단계 드롭다운).
  - 빈 상태 `13320:115837`: "등록된 브랜드가 없습니다." + "브랜드 추가".
  - **삭제**: "삭제" → 확인 알럿 `13320:133199`(문구 §6) → "삭제"를 누르면 서버에서 지우고 목록과 1단계 드롭다운 목록을 다시 읽습니다. 지금 1단계에서 고른 브랜드를 지우면 1단계 브랜드 선택을 비웁니다(다음 1단계 저장에서 `brandIdx: null`). 삭제 실패는 저장 실패와 같은 토스트입니다. 삭제 API(`DELETE /v3/brand/{brandIdx}`, API A-6.3)는 백엔드가 이미 정했습니다: 삭제 표시만 하고, **결제 전 캠페인은 그 브랜드가 비고**(다시 읽으면 `brandIdx`·`brandName`·`brandLogoUrl`이 `null`, 다시 고르게 함) **결제한 캠페인은 그대로 보이며**, 불러오기 원본의 브랜드가 지워졌으면 비웁니다(REQ-10-0028과 같음). 승인 대기·진행 중 캠페인이 쓰는 브랜드도 막지 않습니다.
  - **브랜드 추가** `13320:115525`(헤더 "<" + "브랜드 관리" + "×", 소제목 "브랜드 추가"): **브랜드명* 한 칸**(국문·영문 구분 없음, REQ-10-0018)을 받고, 브랜드 이미지는 선택이며 올리지 않으면 기본 프로필을 씁니다. 같은 브랜드명도 등록할 수 있습니다. "<"는 브랜드 관리 목록으로 돌아갑니다.
  - "저장"은 브랜드명을 입력했을 때만 활성입니다. 저장하면 브랜드 목록을 다시 읽고 새 브랜드를 1단계 브랜드로 선택한 채 드로어를 닫습니다(전의 결정 유지, 시안에 저장 후 화면 없음). 저장이 실패하면 **토스트** "저장에 실패하였습니다. 다시 시도해 주세요."(`13320:115608`, 전의 오류 알럿 결정을 시안으로 대체)를 띄우고 입력값을 그대로 둡니다(REQ-10-0020).
  - 이미지는 미리보기와 Hover "×" 삭제가 있고, TAB·MO는 썸네일을 다시 누르면 파일을 다시 고릅니다(주석 원문). 형식·용량은 **JPG·PNG, 10MB 이하**이고(REQ-10-0019), 서버가 확장자가 아닌 실제 파일 형식도 검사합니다. 어긋나면 올리지 않고 파일 오류 토스트(§6)를 띄웁니다.

### 3단계 인플루언서 조건

- 플랫폼*은 1개만 고릅니다. 인스타그램·블로그·페이스북·유튜브·틱톡·엑스(시안 순서와 표기)이고, 아이콘 토글입니다.
- 선호 성별*은 여성·남성·전체 중 1개입니다.
- 선호 연령대*는 10대~50대 이상에서 1개 이상, 포스팅 주제*는 1개 이상 고릅니다. **주제 목록은 서버 기준을 따릅니다**(사용자 답 2026-11-12 P-25, 시안 8개·명세 20개가 달라서). 서버가 코드 21개를 정해 줘서(아래) 개수가 늘어도 토글이 줄바꿈되게 둡니다. 최대 개수 제한은 없습니다.
- 포스팅 주제 코드는 서버의 인플루언서 카테고리 대분류 20개 + "전체"(`All`) 21개입니다(API 코드 표 `topics`, 값은 `trans_key` 표기 그대로). 목록 조회 API는 없어 프론트가 코드 목록을 두고 번역 키로 이름을 보여 줍니다(코드 표의 한국어 이름). 시안 8개와 다르고, "전체"를 다른 주제와 함께 고를 수 있는지는 P-30입니다. **이 단계는 서버가 연령대·주제가 비어 있으면 저장을 거절**해서(API A-5.3), 둘 중 하나라도 비어 있으면 단계를 옮길 때 이 단계 저장을 건너뜁니다(고른 플랫폼·성별도 저장되지 않음, 백엔드에 완화 요청 Q-16).
- 플랫폼은 5단계 필수 해시태그 칸 구성을 정합니다(REQ-10-0039). 플랫폼을 바꾸면 5단계 해시태그를 새 칸 기준으로 다시 검사합니다(§3 5단계).
- 기존 `entities/platform`은 인플루언서 검색용(4개)이라 쓰지 않습니다. 캠페인 플랫폼 6개는 `entities/campaign`이 소유합니다. 아이콘만 `PlatformIcon`을 늘려 함께 씁니다(소비처 확인).

- **AI**: 상품/서비스 URL*을 넣고 "AI 생성"을 누릅니다. 생성 중에는 안내(`Message Alert`, 취소 없음)를 띄우되 **다른 단계로 이동해 계속 작업할 수 있습니다**(사용자 결정, 5분 동안 기다리지 않게). 생성 중에는 5단계 입력칸만 잠그고, 작업 id를 초안에 남겨 새로고침해도 이어서 기다립니다. **단, 백엔드 개편(2026-11-12)에서 AI 소개서 생성 API와 `intro.mode`·`intro.aiJob` 저장이 범위에서 빠졌습니다**(API Q-17). 답 전에는 AI 작성은 개발 서버 목에서만 동작하고, 작성 방식은 서버에 남지 않아 다시 들어오면 입력값이 있으면 "직접 작성하기"로 엽니다. 등록 내역 5번의 "작성 방식" 행도 Q-17 답 전에는 그리지 않습니다. 5단계가 아닌 곳에 있을 때 끝나면 토스트로 알리고 사이드바 5단계에 "생성 중"·완료 표시를 보입니다(시안 대기). 끝나면 별도 카드 "AI 생성"에 메인 이미지·상세 미디어·설명·유의사항·해시태그를 채우고, 사용자가 고칠 수 있습니다. "다시 생성하기"는 확인 없이 **소개서 전체**(AI 결과와 사용자가 고친 내용 모두)를 새 결과로 덮어씁니다(REQ-10-0057). 생성 실패는 토스트이고 기존 입력은 그대로 둡니다. 생성 결과가 있어야 결제 전 검사를 통과합니다.
- 공통 필드
  - 메인 이미지*: 1장, JPG·PNG 10MB, 권장 1200×630. 미리보기·삭제·다시 올리기가 있고, AI가 만든 이미지를 지우면 그 이미지만 빠집니다(REQ-10-0059)

  - **필수 해시태그는 3단계 플랫폼에 따라 칸이 다릅니다**(REQ-10-0063~0065, 직접 작성 예시 `13320:117723`·`13320:117748`): 네이버 블로그·유튜브는 "제목 필수 해시태그"* + "본문 필수 해시태그"* 두 칸, 인스타그램·틱톡·페이스북·엑스는 "필수 해시태그(키워드)"* 한 칸(본문 키워드로 저장)입니다. 플랫폼을 아직 고르지 않았으면 한 칸으로 보여 줍니다. 칸마다 Enter로 칩 추가, 칩 "×"로 삭제, 1개 이상, 같은 칸 안에서 같은 값은 넣지 않습니다. 제목·본문 키워드는 따로 저장합니다. 플랫폼을 바꾸면 새 칸 기준으로 다시 검사합니다(제목 칸이 없어지는 플랫폼으로 바꿀 때 제목 키워드를 지울지는 P-22, 답 전에는 지움)
- **AI 시안 프레임으로 통일합니다**(사용자 결정, D-7): 캠페인 설명·유의사항 상한은 직접 작성도 AI 결과와 같은 **1000자**, 필드 구성·순서도 AI 결과 프레임과 같습니다. 개정 명세서 REQ-10-0061·0062는 AI·직접 작성 모두 300자라 여전히 다릅니다(D-7). **API(A-5.5)는 설명 최대 300자(확정 전)·유의사항 최대 3줄·줄당 150자**라, 지금 화면 한도(1000자, 줄 제한 없음)로 쓰면 저장이 거절될 수 있습니다. 백엔드에 맞춤을 요청했습니다(Q-18).

- **미리보기**: 내용이 없으면 비활성이고, 미리보기 화면은 시안이 없어 버튼만 둡니다(동작 없음, D-8).

### 6단계 진행 조건

- 포스팅 유지기간*: 1·3·6·12개월·직접 입력이고, 직접 입력이면 "개월" **정수 1~999**를 받습니다(REQ-10-0068·0069). 범위를 벗어나면 입력 아래 오류 문구(§6)를 보이고 결제 전 검사에서 막습니다.
- 2차 저작권 사용 여부*: 사용 / 미사용(세부 정책은 명세서도 추후 확정, REQ-10-0070)
- PICK형은 제안금액·원고컨펌료를 **모두 매칭 단계에서 결제**하고 등록 결제에 넣지 않습니다(REQ-10-0071·0075). 일반 리워드 입력도 없습니다.
- 리워드*는 **모집형 제품발송형에만** 있습니다(사용자 결정: PICK형은 리워드 없음, 기자단형·매장방문형도 리워드 없음, 구매리뷰형은 스펙아웃. 모집형 3.0.3의 "리워드 제공 여부(제공·미제공)" 추가와 "최대 금액 표기 삭제"는 모집형 갱신 때 반영, 유형 범위·상한은 P-35). 원 단위 1원 이상이고 **상한은 협찬제품 금액**(제품 1개당)입니다. 도움말은 3.0.2 기준 "최대 {금액}원까지 가능하며 입력한 리워드 금액은 캠페인 종료 후 최종 정산 금액에 반영됩니다."이고, 3.0.3 시안은 "리워드 금액은 캠페인 종료 후 최종 정산 금액에 반영됩니다."로 상한 문구를 지웠습니다(P-35 답에 따라 바꿈).
- 리워드는 **인플루언서 1인당 금액**입니다(REQ-8-0017).
- 진행 인원*(모집형): 숫자 스테퍼(− n 명 +)이고 1명 이상입니다(제한 없음, 사용자 결정).

### 7단계 캠페인 정책 동의

- "약관 전체 동의"는 필수 4개(서비스 이용약관·개인정보 처리방침·캠페인 운영 정책·리워드 및 결제 관련 정책)를 한꺼번에 켜고 끕니다. 4개가 모두 켜지면 전체도 켜집니다.
- 항목의 ">"를 누르면 약관 전문을 엽니다(PC·TAB 다이얼로그, MO 전체 화면). "동의하기"는 그 항목을 켜고 닫고, "취소"는 닫기만 합니다.
- 전문은 `entities/terms`가 갖습니다. 서비스 이용약관·개인정보 처리방침은 있는 본문을 쓰고, **캠페인 운영 정책·리워드 및 결제 관련 정책도 프론트가 관리합니다**(사용자 결정). 두 정책은 원문이 없어 원문을 받을 때까지 ">"를 숨기고 체크만 받습니다(P-14).
- 4개 모두 동의해야 결제 전 검사를 통과합니다. 개정 명세서는 약관 항목·필수 여부를 "추후 확정"으로 두었으므로(REQ-10-0076·0077) 확정되면 바꿉니다. 지금은 시안대로 4개 모두 필수입니다.
- 동의는 캠페인마다 새로 받고 이전 캠페인 불러오기로 복사하지 않습니다. 동의 이력(항목·약관 버전·일시)은 서버가 저장 요청 때 기록합니다(REQ-10-0079).

### 8단계 결제

- 카드 4개로 구성합니다: PC는 2×2이고, TAB·MO는 캠페인 요약 → 결제 수단 → 결제 요약 → 약관 동의 순서로 세로입니다.
- **금액은 프론트가 초안 값으로 계산합니다**(사용자 결정, 규칙이 단순함, REQ-8-0058 "실제 설정된 내역 기준"). `calculatePayment`가 한 곳에서 계산하고 화면은 그 결과만 씁니다. 단가·계산식: AI 포스팅 가이드 10,000원 정액, 원고컨펌·AI 영수증 리뷰(모집형만) 인원당 5,000원 × 진행 인원, 리워드(모집형 제품발송형만) = 1인당 리워드 × 진행 인원, 총 결제 금액 = 부가서비스 합 + 리워드 총액(시안 예시 수치와 맞음). 결제 요약의 부가서비스 행은 고른 것만, 리워드 행은 모집형만 보여 줍니다. **PICK형 등록 결제는 AI 포스팅 가이드 10,000원뿐입니다**(REQ-10-0080): 원고컨펌은 골라도 등록 결제 상품·금액에 넣지 않고(매칭 단계 결제, 결제 요약에 "매칭 시 결제" 안내를 따로 두지 않음 — 시안에 없음), AI 포스팅 가이드를 고르지 않으면 총액이 0원입니다. PICK형 결제 요약 시안의 "(건별 5,000원 * 모집인원 400명)"은 잔재라 그리지 않습니다. PICK형 캠페인 요약은 서비스 유형 · 캠페인 유형 · 리워드 · 캠페인 기간이고, **리워드 행은 "제품 제공 ({협찬제품 금액}원 상당)"으로 제품 1개당 금액을 그대로 보여 줍니다**(1인당 제공 수량을 곱하지 않음, 제품발송형만, 사용자 답 2026-11-12 P-2). PICK형 리워드는 광고주가 인플루언서에게 주는 것이라 빅버드 결제 금액이 아니어서 결제 요약·총액에 넣지 않습니다. 반면 모집형 리워드는 결제 금액이라 1인당 리워드 × 진행 인원으로 결제 요약에 더합니다. 시안에 새로 생긴 "구매 지원금" 행은 구매리뷰형 스펙아웃으로 그리지 않습니다. 개정 명세서 REQ-10-0080은 "캠페인 정보·선택 유형·등록 시 과금되는 부가서비스와 금액"으로 시안 구성과 맞습니다. REQ-10-0081의 "결제 예정 금액·결제 후 예상 잔액"은 시안에 없어 넣지 않습니다. "VAT 등 실제 적용되는 결제 정책에 따라 금액 표시"(REQ-10-0080)는 지금 정해진 VAT 정책이 없어 공급가 그대로 보여 주고, 정책이 나오면 `calculatePayment`에 반영합니다. 0원이어도 버튼은 그대로 "결제하기"이고 승인 요청 역할을 합니다(잔액 검사 생략, 사용자 답 2026-11-12 P-2). 돈이 오가므로 서버는 결제 요청의 `expectedTotalAmount`를 다시 계산해 다르면 거절하고, 프론트는 이때 `AMOUNT_CHANGED` 안내를 보입니다. 사용자가 앞 단계를 채우지 않고 8단계에 와도 있는 값으로 계산해 보여 줍니다.
- 결제 수단은 "빅버드 머니"(라디오 선택 고정 + "필수" 배지)이고, 보유 빅버드 머니는 헤더 P와 같은 잔액 SWR 키를 씁니다.
- **충전 영역**(충전 금액 입력·빠른 금액·"충전하기")은 시안대로 둡니다(사용자 결정). "충전하기"를 누르면 마이페이지 빅버드 머니 충전과 같이 약관 팝업 → 충전 요청(이니시스 무통장 입금) 순으로 갑니다. 금액 규칙·빠른 금액·안내 문구는 [money.md](../mypage/money.md)를 따르고(개정 명세서 REQ-10-0082의 빠른 금액 10만·50만·100만·1,000만 원과 같음, 시안의 "최소 1,000원"·1/3/5/10만 원은 옛 값), 결제창 복귀 주소는 쿼리 없이 `/campaign/register/:id`로 보냅니다(결제 서버가 뒤에 `?isPaid=…`를 문자열로 이어 붙이므로 마이페이지와 같은 방식이고 백엔드 변경이 없음, 사용자 결정 2026-11-06). 작성 페이지는 `isPaid`가 오면 8단계(`step=payment`)로 열고, `isPaid=true`면 접수 알럿("충전 요청 접수", 마이페이지 문구)을 띄운 뒤 결제 서버가 붙인 쿼리를 지웁니다(마이페이지 `usePaymentReturn`과 같음). **무통장 입금은 입금이 확인돼야 잔액이 늘어서, 요청 직후에는 여전히 잔액 부족일 수 있습니다.** 시안의 즉시 "충전 완료" 알럿은 만들지 않습니다. 충전 UI는 `features/charge-bigbird-money`의 것을 쓰는데 feature끼리는 서로 가져올 수 없어서, 마법사는 `chargeSlot`을 받고 페이지가 채웁니다(§4).
- 약관 동의 카드는 7단계와 **같은 값**을 보여 주고 여기서 고쳐도 7단계에 반영합니다.
- "결제하기"를 누르면 다음 순서로 처리합니다.
  1. 모든 단계를 검사합니다. 비어 있는 단계(약관 미동의 포함)가 있으면 필수 항목 미입력 알럿을 띄우고 확인하면 첫 미완 단계로 보냅니다.
  2. 총액이 0원보다 크고 잔액이 총액보다 적으면 "결제 금액 부족" 알럿을 띄웁니다. 개정 명세서는 이 팝업에서 충전으로 들어갈 수 있게 하라고 합니다(REQ-10-0083). 알럿 버튼은 "확인" 하나이고, 누르면 같은 화면의 충전 영역으로 스크롤하고 충전 금액 입력에 포커스를 줍니다(사용자 답 2026-11-12 P-29).
  3. 결제를 요청합니다. 요청 중에는 "결제하기"를 로딩·비활성으로 두어 다시 누를 수 없게 하고, 서버도 같은 캠페인 결제를 한 번만 처리합니다(REQ-10-0085). 서버는 필수값·자격 조건·**PICK형 구독 유효 여부**·잔액·총액을 다시 검사합니다(REQ-10-0084). 성공하면 "결제 완료" 알럿을 띄웁니다. 완료 알럿은 "확인"만 두고(빅버드 머니 스펙과 같은 규칙), "확인"을 누르면 `/campaign/:campaignId`로 `replace`합니다.
  4. 실패하면 **오류 알럿**을 띄우고(REQ-10-0087, 시안 없음, 문구 §6) 등록 중 상태와 입력값을 그대로 두어 다시 결제할 수 있게 합니다. 서버 오류 코드별 처리(API A-9): `INSUFFICIENT_BALANCE` → 결제 금액 부족 알럿, `INCOMPLETE_DRAFT`·`POLICY_NOT_AGREED` → 필수 항목 미입력 알럿 후 `missingSteps` 첫 단계(서버 단계 이름 `info`를 주소의 `campaign-info`로 바꿈), `INVALID_START_DATE` → 안내 알럿 후 1단계, `SUBSCRIPTION_REQUIRED` → 구독 안내 알럿("구독하기"), `AMOUNT_CHANGED` → 다시 계산해 새 금액 표시, `ALREADY_PAID` → 상세 다시 읽기(승인 대기면 등록 내역으로). 앞의 두 안내 문구는 §6(P-30).
  5. 결제는 성공했는데 화면 이동이 실패했으면, 다시 들어올 때 캠페인 상태(승인 대기)를 보고 등록 내역으로 보냅니다(§3 상태별 진입, REQ-10-0088).
- **결제 완료가 곧 승인 요청**입니다(시안·REQ-10-0086·0091). 별도 "승인 요청" 버튼은 없습니다.

### 데모 모드 (PICK형)

**구현 범위입니다**(사용자 결정 2026-11-12, 전의 "범위 밖" 결정을 대체). 규칙은 개정 명세서 2026-11-12 추가분(REQ-10-0001·0009·0013·0080·0081, 데모 제공·입력 보존·불러오기·화면 표시·결제 단계·작성 완료·기본 정보 안내·실제 전환, 원문은 캐시 `req-campaign-register-pick.md`)입니다. **데모 화면 시안은 아직 없습니다**(D-17).

**생성·상태**
- PICK형을 **구독하지 않은** 광고주만 새 데모를 만듭니다. 개설 화면 PICK형 상품 카드의 "데모 캠페인 등록"으로 들어오고, 구독 중이면 새 데모를 만들 수 없습니다(개설 화면이 막고 서버도 거절). 주소는 `/campaign/register?type=pick&demo=true`(만든 뒤 `/campaign/register/:campaignId`로 교체)이고, 만든 뒤에는 데모 여부를 서버 캠페인 값으로 판단합니다.
- 서버는 구독 없이 캠페인 코드를 만들고 등록 중으로 저장합니다. 데모 여부·작성 완료 여부를 따로 가지며, **대표 상태는 작성 중이든 작성 완료든 늘 "등록 중"**입니다. 결제·승인 요청·캠페인 운영은 할 수 없습니다.
- 작성 중·작성 완료 데모 모두 캠페인 현황 "등록 중" 목록에 **DEMO 태그**와 함께 보이고, 등록 중과 같이 **지울 수 있습니다**(지우면 불러오기 목록에서도 빠짐). 데모는 횟수 제한 없이 만들 수 있고, **구독 전에 만든 데모는 구독한 뒤에도 조회·이어 쓰기**가 됩니다(구독 중에는 새 데모 생성만 막음). 현황 바로 가기는 작성 중 "작성하기", 작성 완료 "등록 내역"입니다(REQ-4-0022·0023, REQ-5-0015·0024·0026·0027, [status](./status.md)).

**작성 중**
- 입력 필드·필수값 검증·사이드바·단계 이동·저장은 실제 등록과 같고, 다시 들어오면 저장된 단계와 입력값으로 이어서 씁니다. 구독 재검증은 하지 않습니다.
- 헤더 제목은 **"캠페인 등록 [DEMO]"**입니다.
- 모든 단계 하단 바 **왼쪽**에 안내 아이콘 + 두 줄 안내(단계마다 같은 문구, §6)를 두고, 오른쪽 버튼(임시저장·이전·다음)은 그대로입니다. MO는 하단 바가 버튼만으로 차서 안내 위치는 D-17입니다(답 전에는 하단 버튼 바로 위에 같은 두 줄).
- 7단계 캠페인 정책 동의는 실제 등록과 같이 받습니다(실제 전환 때 다시 받음).
- **8단계**: 제목은 그대로 "결제"입니다. **캠페인 요약·결제 요약 카드만** 보이고(실제와 같은 `calculatePayment`로 예상 결제 금액), **결제 수단·빅버드 머니 잔액·충전 카드와 약관 동의 카드는 그리지 않습니다**. 결제 요약 아래에 안내 "데모 모드에서는 실제 결제가 진행되지 않으며, 표시된 금액은 실제 캠페인 등록 시 변경될 수 있습니다."를 둡니다. 하단 버튼은 "임시저장 · < 이전 · **등록 정보 보기**"입니다.

**작성 완료**
- "등록 정보 보기"를 누르면 "결제하기"와 같이 모든 단계를 검사합니다. 실패하면 필수 항목 미입력 알럿 → 첫 미완 단계로 보냅니다.
- 통과하면 확인 알럿 **"데모 작성 완료"**(문구 §6, "취소"·"확인")를 띄웁니다. "취소"는 닫기만 하고, "확인"은 저장 후 작성 완료 요청을 보냅니다. 요청 중에는 버튼을 막고 서버도 한 번만 처리합니다. 성공하면 `/campaign/:campaignId`(기본 정보)로 `replace`합니다. 결제·승인 요청은 없습니다.
- **작성 완료된 데모는 결제를 마친 실제 캠페인(승인 대기)과 똑같이 수정할 수 없습니다**(사용자 결정 2026-11-12): 작성 경로(`/campaign/register/:id`)로 오면 기본 정보로 보내고, 저장·입력 변경 요청은 서버가 거절합니다(`NOT_EDITABLE`과 같은 처리). 바꾸려면 실제 캠페인으로 전환하거나, 새 실제 캠페인에서 이전 캠페인 불러오기로 가져와야 합니다.
- 작성 중 데모의 기본 정보 주소는 작성 경로로 보냅니다(전환 버튼 없음).

**기본 정보 화면 (작성 완료 데모)**
- 실제 등록 내역과 같은 섹션 카드 구성이고, 상태 배너 자리에 **데모 안내 영역**을 둡니다. 제목 "현재 캠페인은 데모 모드로 작성한 캠페인입니다."
- 본문과 버튼은 **들어올 때마다 PICK형 구독 상태를 확인해** 정합니다(`entities/subscription`, 화면에 다시 돌아오면 다시 읽음).
  - 미구독: "데모 모드로 작성한 캠페인은 요금제 구독 시 실제 캠페인으로 전환 가능합니다." + **"구독하기"** → `/mypage/subscribe`
  - 구독 중: "데모 모드로 작성한 캠페인을 실제 캠페인으로 전환 가능합니다." + **"실제 캠페인으로 전환"**
- 화면 동작은 **승인 대기 캠페인의 등록 내역과 같습니다**: 섹션 "수정"·하단 버튼이 없고, 사이드바도 승인 대기 등록 내역과 같습니다. 다른 점은 상태 배너 대신 데모 안내 영역이 있다는 것과, 결제가 없어 8번 결제 정보 섹션을 그리지 않는다는 것(D-17)뿐입니다.

**실제 캠페인으로 전환**
- "실제 캠페인으로 전환" → 확인 알럿(문구 §6, "취소"·"전환하기"). "전환하기"를 누르면 전환 요청을 보내고, 요청 중에는 버튼을 막습니다. 서버는 작성 완료 여부와 PICK형 구독을 다시 검사하고 같은 캠페인의 중복 전환을 막습니다.
- 성공하면 **같은 캠페인이 실제 "등록 중" 캠페인이 됩니다**: 캠페인 코드, 1~6단계 입력값, 부가서비스 선택을 그대로 두고, 데모 여부를 지우며(현황의 DEMO 태그 사라짐) 7단계 정책 동의는 비웁니다. 새 코드를 만들거나 복제하지 않고, 데모로 되돌릴 수 없습니다. 프론트는 `/campaign/register/:campaignId?step=campaign-info`로 `replace`하고, 이후는 실제 등록과 같습니다(7단계 동의, 8단계 결제 수단·약관·결제).
- 실패하면 데모 상태와 입력값을 그대로 둡니다. 구독이 끝났으면 구독 안내, 그 밖은 오류 토스트(§6)를 띄우고 기본 정보 화면을 다시 읽어 안내 영역을 갱신합니다.

**이전 캠페인 불러오기로 쓰기**
- 새 실제 PICK형 브랜드형 캠페인의 불러오기 목록에 작성 중·작성 완료 데모가 모두 나옵니다. 복사 범위·재검증은 일반 불러오기와 같고(§3 1단계), 원본 데모는 그대로 남습니다. 직접 전환과 다른 기능입니다.

## 4. 배치

슬라이스 구성(`pages/campaign-register`·`pages/campaign-detail`·`widgets/app-shell`의 `FocusShell`·`features/register-campaign`·`features/manage-campaign-approval`·`entities/campaign`·`entities/brand`)과 Public API는 코드가 기준입니다. 아래는 코드로 알 수 없는 결정입니다.

- 서비스 유형별 차이는 단계 정의 배열과 단계 컴포넌트 안의 분기로만 둡니다(마법사 골격·주소·저장은 공통). 공구형이 추가돼도 같은 골격을 씁니다.
- 이전 캠페인 불러오기·브랜드 관리(목록·추가·삭제)·AI 생성은 지금 이 마법사에서만 쓰여 `features/register-campaign` 안에 둡니다. 브랜드 목록·추가·삭제 API는 `entities/brand/api`입니다. 마법사 밖(예: 마이페이지)에 브랜드 관리 화면이 생기면 그때 feature로 뺍니다.
- **`AppShell`에는 모드를 더하지 않고** 작업 전용 셸 `FocusShell`을 새로 둡니다(사용자 확인). 헤더 오른쪽 묶음(포인트·알림·프로필)만 두 셸이 같이 씁니다.
- 라우트는 로그인 필요이고 **Sub ID는 캠페인을 만들 수 없습니다**(사용자 결정). `MASTER_ONLY_PATHS`는 경로를 정확히 비교하므로 `/campaign/register`와 `/campaign/register/:campaignId`를 함께 막으려고 접두사 비교로 바꿨고, Sub ID는 계정 설정으로 보냅니다. 등록 내역(`/campaign/:campaignId`)은 막지 않습니다(P-18).
- **feature끼리는 서로 가져올 수 없어서** 결제 화면의 충전 영역은 마법사가 `chargeSlot`으로 받고 페이지가 `ChargeInline`으로 채웁니다(결제창 복귀 주소를 받도록 충전 경로 빌더를 넓힘).
- 목은 개발 서버(`import.meta.env.DEV`)에서만 동작합니다(사용자 결정 2026-11-05: 빌드 변수·CI 변경은 보류, prod 배포 때는 API가 나와 있을 것). stage·prod 빌드에서는 세 경로(작성 둘·등록 내역)가 `pages/coming-soon`입니다. 개발 전용 코드와 목은 번들에 들어가지 않습니다(2026-11-09 `pnpm build`로 확인, 번역 문구만 번들에 있음).

## 5. 데이터 흐름의 예외

- **API 구현 전 → 목.** `features/register-campaign/api`와 `entities/*/api`의 fetcher가 플래그를 보고 목 모듈로 응답합니다. 목도 응답을 Zod 스키마로 검증하고, 스키마와 요청 모양은 API 요구 명세(2026-11-12 개편판)를 따릅니다. API가 나오면 fetcher만 바꿉니다. 목 저장소는 메모리 + `sessionStorage`(새로고침해도 이어 쓰기 확인용)입니다.
- **fetcher 소유**: 캠페인 하나를 읽고 바꾸는 API는 같은 목 DB를 읽고 써서 `entities/campaign/api`가 갖고, DB와 무관한 파일 업로드·AI 생성(목 전용, Q-17)은 `features/register-campaign/api`, 브랜드는 `entities/brand/api`입니다. 목은 빅버드 머니 잔액 API(실제 서버)를 바꿀 수 없어 결제·환불 응답의 `balance`는 0이고, 화면은 잔액 API를 다시 읽습니다. 개발 서버에는 검토중 캠페인을 반려·승인 완료로 바꾸는 확인 버튼이 있습니다.
- **SWR 캐시 함정**: 결제·승인 요청 취소·초안 저장 뒤에는 등록 내역 캐시를 비워 다음에 새로 읽게 합니다. 이때 SWR의 요청 중복 방지(기본 2초)가 켜져 있으면 직전 조회가 2초 안에 끝난 화면으로 돌아왔을 때 새 조회가 건너뛰어져 로딩에 멈추므로 등록 내역 조회는 중복 방지를 끕니다. 또 저장 직후 화면을 옮기는 쪽이 있어 저장은 캐시 갱신(`onSaved`)이 끝난 뒤에 저장 완료로 알립니다.
- **이전 캠페인 불러오기 복사는 서버가 합니다**(copy API, REQ-10-0026~0029). 캠페인 하나를 바꾸는 API라 fetcher는 `entities/campaign/api`에 두고, 응답 본문이 없어 끝나면 상세(A-3)를 다시 읽고 그 값으로 마법사 store를 한 번 다시 채웁니다. 아래 "한 번만 채움" 원칙의 예외입니다. 복사 뒤 지난 희망 시작일은 오늘로 바꿔 1단계 API로 저장합니다(서버가 하지 않음).
- **마법사 store가 작성 중 초안을 소유합니다.** 이것은 기본 원칙("서버 데이터를 Zustand에 복사하지 않음")의 예외입니다.
  - 진입할 때 서버 초안(SWR)으로 **한 번만** 채우고, 그 뒤 원본은 store입니다.
  - 저장 응답은 SWR 캐시만 갱신하고 store를 다시 채우지 않습니다. 입력 중인 값이 저장 응답으로 되돌아가지 않게 하기 위해서입니다.
  - store는 `features/join`처럼 Provider 안 context store입니다. 캠페인마다 새로 만들고, 화면을 떠나면 버립니다.
- **저장은 단계별 PUT입니다**(API A-5.x, 2026-11-12 개편). store가 단계별로 마지막 저장 값을 기억해 **바뀐 단계만** 보내고, 응답 본문이 없으므로(1단계만 `endDate`) 저장 뒤에는 SWR 캐시를 갱신 표시만 하고 store는 그대로 둡니다. 서버는 단계 단위로 덮어써서 보낸 단계의 빈 칸은 `null`로 비웁니다. 진행 중인 AI 생성 작업 id는 서버에 저장되지 않습니다(Q-17). 사이드바의 활성·입력 중·경고 표시는 저장하지 않고 초안 값에서 계산합니다(3.0.3 사이드바는 "가 본 단계"를 쓰지 않아 `visitedSteps`는 반영 때 없앰).
- 등록 내역·잔액은 store가 아니라 SWR로 읽습니다. 결제 금액은 서버에서 읽지 않고 초안 값으로 계산합니다(§3 8단계).

  3. 1단계 필수값이 빠진 채 "다음"을 누르면 알럿("확인" 하나)이 뜨고 단계가 그대로입니다. 2~7단계 "다음"은 비어 있어도 이동합니다. 입력만 하고 기다려서는 저장되지 않고, 단계 이동·"임시저장" 때 저장되는지(임시저장 토스트), 이동 직전 저장 실패면 이동하지 않는지 확인합니다.
  4. 1단계: 브랜드 메뉴(맨 위 "브랜드 관리", 8개 넘으면 스크롤)를 확인합니다. 브랜드 관리는 목록·개수·빈 상태, 삭제 알럿 → 목록·드롭다운 갱신(지금 고른 브랜드를 지우면 선택이 빔), "브랜드 추가"(브랜드명 한 칸·저장 활성 조건·저장 실패 토스트와 입력 유지·"<"로 목록 복귀), 저장 후 1단계 선택 상태, PC 드로어 / TAB·MO 서브 화면, 뒤로가기로 닫힘을 봅니다. "임시저장" 성공·실패 토스트가 시안 문구인지 봅니다. 캘린더는 PC 팝오버 / MO 바텀시트이고 오늘 이전 날짜가 비활성이며, 날짜를 고르면 라벨이 "캠페인 기간"(시작일·자동 종료일)으로 바뀝니다. 이전 캠페인 불러오기는 검색, 무한 스크롤, 빈 상태 2종, 1개 선택(전체 선택 체크박스 없음), 입력한 값이 있을 때 덮어쓰기 알럿, 불러온 값 반영(약관 동의 제외)을 봅니다. 유형을 바꾸면 2~7단계에 입력한 값이 있을 때 시안 문구 알럿이 뜨고 2~7단계 값이 모두 지워지며 1단계 값은 남습니다.
  5. 2단계: 유형 표시 없이 유형별 필드, 반품 회수 여부 필수(기본 "회수 안함"), 매장방문형 상세 주소 칸, 회수 있음·대여 상품 펼침, 금액 100만원 미만이면 대여 비활성이고 금액을 내리면 일반으로 되돌아감, 캠페인 유형이 3개(구매리뷰형 없음)인지, 기자단형은 입력 없이 결제 전 검사를 통과하는지 확인합니다. 주소 검색은 Daum 우편번호 팝업에서 고른 주소가 읽기 전용 주소 칸에 들어가고 상세 주소만 직접 입력되는지, 스크립트 로드 실패 시 토스트가 뜨는지 봅니다(테스트는 래퍼를 모킹).
  6. 3·4단계: 단일·복수 선택, 선택 스타일이 포커스와 구분됨, 4단계는 PICK형 카드 2장(AI 포스팅 가이드 · 원고컨펌) / 모집형 3개(이름 "원고컨펌"), 부가서비스 없이 통과를 확인합니다.
  7. 5단계: AI 생성 중 안내가 뜨고 다른 단계로 이동해 작업할 수 있는지(5단계 입력칸만 잠김), 새로고침해도 이어서 기다리는지, 끝나면 토스트와 결과 채움, 다시 생성, 실패 토스트를 봅니다. 직접 작성은 AI 결과와 같은 필드 순서이고, 업로드(형식·용량·5개), 드래그, 삭제, 해시태그 Enter·중복·삭제와 플랫폼별 칸(블로그·유튜브 제목+본문, 그 밖은 한 칸), 설명·유의사항 글자 수 카운터와 1000자 상한(300자는 2단계의 방문 혜택·구매 안내만), 미리보기 비활성/활성을 봅니다.
  8. 6단계: 직접 입력 개월(1~999, 밖이면 오류 문구), 모집형 제품발송형은 진행 인원 + 유지기간·2차 저작권 + 리워드, 기자단형·매장방문형은 리워드 없음을 확인합니다. 리워드 상한이 협찬제품 금액이고 도움말에 그 금액이 들어가는지 봅니다.
  9. 7단계: 전체 동의 연동, 약관 전문(PC·TAB 다이얼로그 / MO 전체 화면) "동의하기"로 체크, 운영·리워드 정책은 ">" 없음을 확인합니다.
  10. 8단계: 계산한 금액(부가서비스 합·모집형 리워드 행·총액)이 맞는지, PICK형은 원고컨펌을 골라도 AI 포스팅 가이드만 청구되는지, AI 포스팅 가이드를 고르지 않은 PICK형(0원)도 "결제하기"가 승인 요청이 되는지, 앞 단계를 비운 채 들어와도 계산되는지, 비어 있는 단계가 있을 때 "결제하기" 알럿과 첫 미완 단계 이동, 잔액 부족 알럿(확인 → 충전 영역으로 이동), 결제 중 버튼 비활성, 결제 실패 알럿, 결제 완료 → `/campaign/:id` 승인 대기, "충전하기" → 약관 팝업 → 충전 요청 → 복귀 시 `isPaid` 쿼리로 8단계가 열리며 접수 알럿이 뜨고 쿼리가 지워지는지(`step=payment`)를 확인합니다. Sub ID는 두 경로에 들어올 수 없는지 확인합니다.
  11. 등록 내역: 상태 3종(승인 대기·승인 반려·진행 중, 개발용 전환 버튼)마다 배너·버튼·섹션 "수정"을 봅니다. 승인 대기·승인 반려에서 승인 요청 취소 알럿(환불 수단·환불 예정 금액) → 환불 + 등록 중 → 환불 완료 토스트 → 작성 화면 `step=payment`로 이동해 다시 결제할 수 있는지, 반려의 보완 요청 메시지(배너 아래), 1·2·3·5·6번 섹션 "수정" → 해당 단계(수정 모드: 사이드바 "기본정보", 4단계 전체·모집형 6단계 인원·리워드·7·8단계 잠금, 어느 단계든 "다음"은 저장한 뒤 내역으로 복귀), 재승인 요청 알럿 → 승인 대기, 4번 섹션 "신청함"/"신청 안함" 배지를 확인합니다. 결제 전 캠페인을 내역 주소로 열면 작성으로, 승인 요청 이후 캠페인을 작성 주소로 열면 내역으로 보내지는지, 할당된 Sub ID는 내역을 볼 수 있고 버튼이 숨는지 봅니다.
  12. 데모 모드: PICK형 미구독 계정으로 개설 화면 "데모 캠페인 등록" → `/campaign/register?type=pick&demo=true` → 데모 캠페인이 만들어져 작성 화면으로 교체되는지, 헤더 "캠페인 등록 [DEMO]"와 모든 단계 하단 안내(MO 포함), 8단계에 요약 두 카드·안내 문구만 있고 결제 수단·잔액·충전·약관 카드가 없는지, "등록 정보 보기" → 전체 검사 → "데모 작성 완료" 알럿 → 기본 정보(데모 안내, 미구독 "구독하기" / 구독 중 "실제 캠페인으로 전환")로 가는지, 작성 완료 데모를 작성 주소로 열면 기본 정보로 가는지, 전환 → 같은 코드로 1단계 작성 화면, 7단계 동의 비어 있음, 8단계 결제 수단 보임, 새 실제 캠페인 불러오기 목록에 데모(작성 중·완료)가 나오는지, 구독 중 계정은 새 데모를 만들 수 없는지 확인합니다.
  13. stage·prod 빌드에서 두 경로가 준비 중 화면인지 확인합니다.
