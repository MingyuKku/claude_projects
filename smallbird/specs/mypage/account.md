## 1. 목적과 범위

- 광고주 Master 계정이 자기 정보·회사 정보·정산 계좌·하위 계정(Sub ID)·알림 수신 동의를 관리합니다. v2 `/account`(섹션 나열 + 모달)를 탭 화면으로 바꿨습니다.
- **Master ID와 Sub ID**: Master ID는 광고주(회사) 계정이고, Master가 직원용 Sub ID를 만들어 권한을 줍니다. Sub ID 목록에 Master는 나오지 않습니다.
- 역할은 세션 `authority`로 나눕니다. Master(MASTER·ADMIN)는 탭 5개, **Sub(SUB)는 "Sub ID 관리"(본인 정보)·알림 설정 2개**이고 간편 로그인 연동·회원 탈퇴·회사정보·계좌정보·Sub ID 관리가 없습니다.
- **Sub ID는 구독에 들어갈 수 없습니다.** 빅버드 머니를 Master와 Sub가 공유하므로 구독도 Master가 결제·관리합니다. `/mypage/subscribe`를 열면 세션 middleware가 안내 없이 `/mypage/account`로 보냅니다(서버도 403).
- 로그인 착지점은 권한과 관계없이 홈(`/`)입니다([../auth/login.md](../auth/login.md)).

### API와 목 데이터 (마이페이지 3종 공통 규칙)

- 공개된 V3 API의 응답이 화면을 그리기에 충분하면 API를 연결하고, 부족하거나 없는 화면만 목을 씁니다. 목은 화면용 뷰모델 타입만 두고 응답 형태를 추측한 Zod 스키마는 만들지 않습니다.
- **목은 개발 서버에서만**(사용자 결정): `import.meta.env.DEV`일 때만 목으로 그리고, 빌드(stage·prod)에서는 그 자리에 `EmptyState`(`construction`, "준비 중인 기능입니다.")를 둡니다. 목 값도 빌드 번들에 들어가지 않게 합니다.
- 목을 쓰는 동안 서버에 반영되는 동작은 성공처럼 보이지 않게, 확인 다이얼로그까지 시안대로 진행하고 마지막 단계에서 "준비 중인 기능입니다." 토스트 후 값을 바꾸지 않습니다.
- API가 공개되면 목 파일·목 분기·임시 코드값을 흔적 없이 지웁니다.
- **남은 목: Sub ID 캠페인 할당만**입니다(B-3·B-6, 임시 코드값 `use-code-label`). `GET /campaign`은 있으나 "진행 상태" 기준이 정해지지 않았습니다. 할당 스위치는 "준비 중" 토스트 후 값을 유지합니다. 그 밖은 모두 실제 API입니다.

### 수정 구조

Master ID 관리(기본 정보)·회사정보·계좌정보는 **보기 → "수정"(계좌 미등록은 "등록") → 관리자 비밀번호 확인(`POST /check/pw`) → 같은 카드가 입력 모드 → 취소·저장 → 보기**입니다.

- 비밀번호 확인은 **화면마다, 수정할 때마다** 다시 묻습니다(통과가 다른 화면으로 이어지지 않음). 오류 문구는 시안에 없어 임시(P-6).
- 시안에 없어 v3가 정한 경우: 등록된 회사정보가 없으면 보기 없이 곧바로 입력 모드(비밀번호 확인 없음), 계좌 미등록 "등록"도 비밀번호 확인을 함.
- 회사정보 일부만 저장에 실패하면 입력 모드에 머뭅니다.
- **Sub ID 본인 정보**는 같은 보기 → 입력 구조지만 **비밀번호 확인이 없습니다**(시안에 알럿 프레임 없음, 사용자 결정). 카드는 "기본 정보" 한 장이고 행은 프로필 이미지·담당자 명·아이디 명·비밀번호·이메일 주소·생성일입니다. **휴대폰 번호 행·인증은 없습니다**(시안). 담당자 명은 이름 수정 API가 없어 읽기 전용입니다(B-20).

| 항목 | 결정 |
|---|---|
| 조회 | Master `GET /master`, Sub `GET /sub/self`(생성일 `created`, 프로필 `profileImageUrl`) |
| 정보 수정 | 프로필 이미지·비밀번호 변경·확인·휴대폰 "인증"(Master만)·이메일. 기본 정보의 이메일은 현재 값, 수정 모드의 이메일은 바꿀 이메일을 입력하는 칸. 하단 왼쪽 "회원 탈퇴"(Master만) |
| 비밀번호 | 빈 칸으로 시작해 바꿀 때만 입력. **현재 비밀번호 칸은 없습니다**(시안, 서버도 새 비밀번호만 받음). 규칙은 회원가입과 같고, 5분 제한(429)·개인정보 포함 거부는 오류 문구. Master `PUT /password`, Sub `PUT /sub/pw` |

| 휴대폰 "인증" | **Master만.** KMC 본인인증(`GET /v3/auth/cert/init?trUrl=<현재 출처>/cert/success` → 복호화 `/cert/decrypte` → "저장"에서 `PUT /modify {certIdx, email}`). PC는 팝업, 터치 기기는 페이지 이동이고 `/cert/success`가 이동 전 화면으로 결과를 돌려보냅니다. 이동하는 동안 이메일 입력은 보관했다 되살리고 비밀번호는 보관하지 않습니다. 중복(`same`·`exist`)·실패·팝업 차단은 칸 아래 안내. v3 도메인이 KMC에 등록되기 전(B-12)에는 Stage에서 인증이 안 되고, 로컬은 `docs/kmc-local-test.md`로 확인 |
| 프로필 이미지(함정) | Master `/profile`, Sub `/sub/profile`(서로 상대 경로는 403). **Sub는 `GET /profile`을 부르지 않습니다**: 세션의 회사 기준이라 Sub가 부르면 Master 이미지가 옴. 이미지가 있으면 PATCH, 없으면 POST. 파일은 시안 기준 JPG·PNG 10MB(서버 한도 500MB보다 좁음) |
| 회원 탈퇴 | **Master만.** ① 약관 → ② "동의 및 탈퇴하기" → ③ 비밀번호 확인(`POST /check/pw`, `result: true`가 일치) → ④ `PUT /exit`(v2의 `POST /transfer/false`는 v3에서 필요 없음) → ⑤ 완료 알럿 → `useLogout`(실패해도 진행) 후 로그인 화면. PC·TAB은 중앙 다이얼로그, MO는 전체 화면. 약관은 v2와 같은 **서비스 이용약관**(6조 회원탈퇴 포함)이고 시안 MO 약관 박스의 개인정보처리방침 문구는 자리표시자입니다. v2의 체크박스·"아니요/예"는 시안에서 버튼 하나로 합쳐졌습니다. **③·⑤는 시안이 없어 v3 임의 구성**(P-2): ③ 안내문 + 비밀번호 한 칸 + "취소"·"탈퇴하기", ⑤ "확인"만 있고 닫기·Esc로 벗어나지 못함. 비밀번호 단계는 URL에 남기지 않아 새로고침하면 약관부터 |
| 간편 로그인 연동 | **Master만.** 카카오·네이버·구글·애플 4개, **페이스북은 연동하지 않아 시안에 있어도 그리지 않습니다**(사용자 결정). 상태는 `GET /account/sns`로 읽고 Master 정보의 SNS 필드는 쓰지 않습니다. 즉시 반영이고 저장 버튼과 무관합니다. **끄기**: 확인 알럿(시안 없음, 삭제 알럿과 같은 구조) → `DELETE` → 응답 상태로 스위치 갱신, 이미 해제(404 `SNS_NOT_LINKED`)면 안내 후 해제로 맞춤. **켜기**: 공급자 인가 코드를 `POST`(카카오·구글·애플 `{code, redirectUri}`, 네이버 `{code, state}`, `{token}`은 400). 카카오·네이버·구글은 공급자 화면으로 전체 이동했다 로그인과 같은 콜백 `/auth/{platform}`으로 돌아와 저장해 둔 연결 의도·`state`로 구분해 이어 가고([login.md](../auth/login.md) "SNS 로그인"), 애플은 팝업. 창을 닫으면 안내 없이 끝. 공급자 콘솔에 환경별 리다이렉트 URI 등록 필요(B-10) |

|---|---|
| 목록 | 검색 + "Sub ID 생성"(MO는 하단 고정). **PC만 표**(아이디(아바타)·담당자명·이메일·생성일·관리: 권한 부여·수정·삭제), TAB 카드 2열, MO 카드 1열. 아바타는 `profileImageUrl`, 없거나 열리지 않으면 기본 아바타. 시안의 "(Admin ID)" 행은 무시. 검색·쪽 나눔은 서버(`GET /sub`, 한 쪽 8개, `keyword` 하나로 아이디·담당자명·이메일 검색). 범위를 벗어난 쪽(마지막 항목 삭제 등)은 마지막 쪽으로 당김. 결과 0건이면 페이지네이션 숨김 |
| 빈 상태 | 0건 "Sub ID가 없습니다." / "Sub ID가 필요하다면 추가 계정을 생성해주세요.", 검색 없음은 공통 문구 |
| 생성 | 프로필 이미지(선택)·담당자 명*·아이디 명* + "중복 확인"·비밀번호*·비밀번호 확인*·이메일 주소*. 휴대폰 번호 칸 없음(시안, 서버도 받지 않음). 아이디는 **중복 확인을 통과해야** 하고 값을 바꾸면 다시 확인(v2 버그 수정). 이미지는 생성 요청에 multipart로 함께 보냄. **이미지 저장만 실패해도 계정은 만들어져** 생성 성공으로 처리합니다(다시 보내면 `existing id`) |
| 수정 | 행의 연필 → Master가 Sub ID 정보를 고치는 "Sub ID 수정"(생성과 같은 폼·배치). 비밀번호는 빈 칸으로 시작해 바꿀 때만 입력하고, 비밀번호를 서버에서 읽을 수 없어 바꿀 때만 입력하지만, 비밀번호·비밀번호 확인의 필수 표시 `*`는 **시안대로 수정 모드에도 둠**. 아이디를 바꾸면 중복 확인 필요. 바뀐 값(새 이미지 포함)이 없으면 "수정하기" 비활성. `PATCH /sub/{accountIdx}`로 바뀐 필드만 보내고(이미지 저장만 실패하면 생성과 같이 저장된 것으로 처리), **아이디·비밀번호를 바꾸면 그 Sub는 서버에서 로그아웃**됩니다 |
| 권한 부여 | "Sub ID 권한부여" 패널 안에 "서비스 권한 \| 캠페인 할당" 탭. PC 오른쪽 패널, TAB 목록 자리를 덮는 카드(탭 줄 유지), MO 서브 화면. 열어 둔 행은 활성 표시. **저장 버튼 없이 스위치마다 즉시 저장**: 먼저 반영하고 실패하면 되돌림 + 오류 토스트. 다른 행을 누르면 그 행으로 바뀌고, 목록을 다른 쪽으로 넘기면 열린 패널(권한·수정)은 닫힘. 지금 보이는 목록에 없는 `subId`는 열지 않음 |
| 권한 항목 | 6개를 이 순서로: 캠페인·인플루언서 매칭·인플루언서 마켓·커머스 관리·빅버드 머니·구매자 문의. `GET·PUT /authorization`은 권한별 boolean 필드이고 `PUT`은 바꾼 필드만. 권한이 없으면 LNB 메뉴가 흐리게 비활성([main.md](../main.md)). 고객센터가 아니라 **구매자 문의**인 이유: 빅버드 문의는 막지 않고 광고주↔구매자 창구만 막기 위해서 |
| 캠페인 할당 | 모든 기기 카드(캠페인명·상품 유형·세부 상품·캠페인 진행 상태·담당 여부 스위치, TAB 2열). 할당할 캠페인이 없으면 "할당 가능한 캠페인이 없습니다.". Master의 캠페인을 **페이지 없이 전부**, 진행 완료 포함, 서버 순서(최신순)로. Master는 자기 회사 모든 캠페인의 담당자이고, Sub가 만든 캠페인은 그 Sub에게 자동 할당되며 Master가 해제할 수 있음. 목 단계(§1) |
| 삭제 | Destructive 알럿 "Sub ID 삭제" / "‘{아이디}’를 삭제하시겠습니까? 삭제된 데이터는 복구되지 않습니다." → `DELETE /sub/{accountIdx}` → 목록 갱신. MO는 버튼 세로(삭제 위). 지운 Sub의 패널은 닫음 |

### 알림 설정

## 4. 배치

- 회사정보·계좌정보의 파일 첨부 행은 `shared/components`의 파일 업로드 입력을 공유합니다. 그 밖의 구조는 코드를 봅니다.

## 5. 데이터 흐름의 예외

- 응답 형태가 두 가지(HTTP 상태 + `V3ErrorResponse` / 항상 200 + `result`·`reason`)입니다([docs/mypage-api.md](../../docs/mypage-api.md) §2).
- 폼 상태는 각 feature, 탭·하위 화면 상태는 URL 쿼리가 소유합니다.
- 계좌정보 진입 판정(`isCompanyInfoComplete`)은 Master 조회와 같은 SWR 키를 써서 회사정보를 저장하면 바로 반영됩니다.

## 6. 다국어

- Figma에 없는 문구(간편 로그인 해제 알럿, 저장·생성·삭제 토스트, 중복 확인, 파일 형식, 권한 변경, 회원 탈퇴 비밀번호 단계 등)는 사용자 결정으로 추천 문구를 적용했습니다. 원문은 각 슬라이스의 `locales/ko.json`, 확인할 임시 문구는 §7 P-2·P-6.
- SNS 이름은 서비스 고유 용어가 아니라 브랜드명이라 언어별 통용 표기를 씁니다.
- 서버 값은 `.claude/rules/i18n.md` "서버 데이터"를 따릅니다(마이페이지 3종 공통): 종류가 정해진 값은 코드로 받아 번역 키, 모르는 코드는 서버 값 그대로, DB에 쌓이는 목록 값은 그대로 표시.

| 필드 | 코드 / 그대로 표시 | 한국어 표시 | 사용 화면 |
|---|---|---|---|
| 권한 | 서버 필드 → 프론트 권한 키 → 번역 키 | 캠페인·인플루언서 매칭 등 | Sub ID 권한부여 |
| 상품 유형·세부 상품·진행 상태 | 코드(B-6, 지금은 임시 코드) | 모집형·PICK형 / 브랜드형·공구형 / 진행 완료·대기중·진행중 | 캠페인 할당 |
| 회사 분류·은행명 | 그대로 표시(DB 목록) | 디지털/가전, 신한은행 등 | 회사정보·계좌정보 |
| 캠페인명 | 그대로 표시(사용자 콘텐츠) | — | 캠페인 할당 |

## 9. 검증 시 주의

- 회원 탈퇴는 실제 계정이 탈퇴되므로 목 응답으로만 확인합니다.
- 간편 로그인 켜기·끄기는 실제 연결 상태가 바뀌므로 테스트 계정으로만, 애플은 Stage 배포본에서만 됩니다.

- 목 잔재는 `grep -rn "mock" src/features src/pages src/entities`로 확인합니다. API 공개 전에는 §1의 캠페인 할당(과 구독 이용요약)만 남아야 하고, 빌드 결과(`dist/assets`)에 목 값이 없어야 합니다.
