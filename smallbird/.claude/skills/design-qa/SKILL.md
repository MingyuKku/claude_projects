# 디자인 QA (Figma 시안 ↔ 구현 화면)

Figma 시안이 기준입니다. 구현 화면에서 **디자인·UI 차이만** 찾아 **보고만** 합니다. 코드는 고치지 않습니다(수정은 사용자가 따로 요청).

대상: 사용자가 지정한 페이지(LNB 메뉴) 하나 이상. 기기는 지정이 없으면 시안에 있는 기기 전부(PC 1440 · TAB 768 · MO 360)입니다.

**일은 스크립트가, 판정은 에이전트가 합니다.** 수집·측정·대조는 화면 수와 상관없이 몇 번의 호출로 끝나고(실측 2026-11-13: 시안 수집 0.5초, 측정 화면당 약 1초, 대조 0.1초 미만), 큰 데이터는 파일로만 오갑니다. 에이전트는 차이 후보를 읽고 판정만 합니다. 화면마다 Figma·브라우저를 따로 부르지 않습니다.

## 비교 기준

**시안의 지정값을 화면에 그렸을 때 구현과 같은 결과인지**를 봅니다. CSS 속성이 어느 요소에 붙었는지는 보지 않습니다(대조 스크립트가 padding은 "컨테이너 시작 → 첫 자식 거리", gap은 "자식 사이 거리", 배경은 "보이는 색", 테두리는 "그려진 선"으로 비교).

- 비교 대상: 간격(padding·gap), 크기 방식과 고정 크기, 글꼴(크기·굵기·행간·자간), 색, radius·테두리·그림자·불투명도, 컴포넌트 변형·상태, 아이콘, 요소 유무·순서·정렬.
- 지정값이 다르면 차이가 작아도 보고합니다. 지정값이 같은데 생긴 1px 이하 반올림·렌더링 차이는 보고하지 않습니다.
- 바깥 크기(카드·버튼 높이 등) 차이는 원인을 찾는 **단서**입니다(대조 결과의 "높이 단서"). 원인이 된 안쪽 지정값을 차이로 판정하고, 바깥 크기는 메모에 "N 때문에 높이 X → Y"로 적습니다.
- Figma는 같은 Tailwind 이름이라도 기기별 값이 다릅니다(예: `gap-6` = PC 24 · TAB 20 · MO 16, 텍스트 스타일 `text-sm/leading-5/medium`). 시안 수집 결과의 `vars`가 변수 이름이고 값은 그 기기 모드로 풀려 있습니다. 코드의 대응은 `ds-` 토큰입니다(`.claude/rules/styling.md`).

| 차이로 보지 않음 (지정값이 같을 때만) | 그래도 보고함 |
|---|---|
| 같은 글꼴·크기·굵기·행간·자간인데 글자 폭·줄바꿈이 조금 다름 | 지정 글꼴이 안 불려 대체 글꼴로 그려짐 |
| 같은 아이콘 이름·크기·선 굵기인데 획이 미세하게 다름 | 아이콘 이름·크기·선 굵기가 다름 |
| 반올림으로 생긴 1px 이하 위치·크기 차이 | 지정값이 다른데 차이가 작은 것(예: 행간 22 vs 24) |
| — | 같은 토큰 이름인데 hex가 다름(Figma Tailwind v3 vs 구현 v4 팔레트): `summary`에 "토큰 원본 불일치"로 한 번만 적음(하) |

| 포함 (보고) | 제외 (보고하지 않음) |
|---|---|
| 레이아웃: 배치·정렬·순서·요소 유무·고정(sticky·fixed) 여부 | 상품명·이름·금액·날짜·건수 같은 데이터 값 |
| 간격·크기·색·글꼴·모양(radius·테두리·그림자·불투명도) | 차트 수치, 목록·표의 행 수 |
| 컴포넌트 변형과 상태(hover·focus·disabled·오류) | 이미지 내용, 데이터 길이 때문에 생긴 줄바꿈·폭 차이 |
| 고정 라벨 문구(버튼·제목·placeholder) 누락·오타, 말줄임 vs 줄바꿈 | 시안의 더미 텍스트와 실제 데이터의 차이 |

- 시안끼리 서로 다르면(같은 컴포넌트가 프레임마다 다름) **시안 불일치**로 따로 적고 어느 쪽이 맞는지 추측하지 않습니다.
- 데이터인지 UI인지 애매하거나, 시안에 없는 상태이거나, 원인을 못 찾으면 **확인 필요**로 적습니다.
- 요구명세서와 시안이 다르면 시안 기준입니다.

## 준비물

- **FIGMA_TOKEN**: 메인 폴더 `.env.local`의 `FIGMA_TOKEN`(권한 `file_content:read`, 팀원별 토큰). 없으면 멈추고 사용자에게 요청합니다. 에이전트는 `.env.local`을 읽지 않고 스크립트만 씁니다.
- **개발 서버**: QA를 요청받은 워크트리(현재 작업 폴더)에서 뜬 서버만 씁니다. 떠 있는 서버는 `lsof -a -p <PID> -d cwd`로 실행 폴더를 확인하고, 아니면 `pnpm dev`로 띄웁니다. 내가 띄우지 않은 서버는 종료하지 않습니다.
- **로그인**: 측정 전에 Playwright 브라우저 창(평소 Chrome과 다른 창)에서 사용자에게 로그인을 부탁합니다. 자격 증명은 입력하지 않습니다. 계정 상태(구독 여부·권한)가 시안 프레임 상태와 맞는지 확인합니다.

## 진행

```
디자인 QA 진행:
- [ ] 1. 범위 확정 (화면 목록·비용, 사용자 확인)
- [ ] 2. screens.json 작성 → qa.mjs prepare
- [ ] 3. 측정 (Playwright 2회 호출)
- [ ] 4. qa.mjs compare → 후보 판정 → verdicts.json
- [ ] 5. qa.mjs report → 보고서 열기·요약·브라우저 닫기
```

명령과 파일 형식은 `references/workflow.md`에 있습니다.

### 1. 범위 확정

1. `docs/pages.md`에서 페이지의 URL·탭(`?tab=`)·하위 화면(`?panel=`)·접근 조건을 확인합니다. 경로가 표와 다르면 `src/shared/config/routes.ts`가 맞습니다. `.claude/figma-cache/`의 페이지 문서는 **화면 구성 파악용**으로만 읽습니다(비교 값은 항상 Figma에서 새로 받음).
2. 시안 프레임 찾기: 사용자가 준 페이지·구역 node로 `references/figma-frames.md`의 스크립트를 한 번 돌려 프레임별 node·본문 글자·상태 표시(겹침·메뉴열림·선택된 탭·긴 본문)를 받습니다. 기본 화면에는 `겹침`·`메뉴열림`이 없는 프레임을 고르고, `선택[…]`에 맞춰 URL·`actions`를, `긴본문N`에 맞춰 `viewport` 높이를 정합니다. 프레임 이름은 믿지 않습니다. node를 사용자에게 찍어 달라고 하지 않습니다.
3. **화면 목록**(화면 제목 · 상태 · 기기 · URL · 시안 node)과 **비용**(화면 수, 예상 시간: 수집·측정은 몇 분, 판정은 후보 수에 비례)을 보여 주고 확정받습니다.
   - 상태 프레임(다이얼로그·펼침·오류·hover)은 기본 제외, 요청한 것만 넣습니다. 넣으면 `actions`(클릭·hover)로 상태를 만듭니다.
   - 결제·삭제·탈퇴처럼 데이터가 바뀌는 동작 뒤의 화면은 빼거나 확인 다이얼로그까지만 엽니다.
   - 공통 셸(헤더·LNB)은 기본 제외(`root: "main"`).
4. 이전 보고서: `.claude/figma-cache/qa/<페이지>-*`가 있으면 정리 여부를 묻습니다(`references/report.md`).

### 2~3. 수집·측정

`screens.json`을 보고서 폴더에 쓰고 `prepare` → Playwright 측정 1회 → 측정값 꺼내기 1회. 측정 응답에 `FAIL`이 있는 화면은 원인(대기 문구·상태 동작·로그인)을 고쳐 그 화면만 다시 돌립니다. `scroll`이 나온 화면(본문이 잘림)은 시안이 긴 프레임이면 `viewport` 높이를 늘려 다시 잽니다.

### 4. 판정

`compare`가 화면마다 후보(`c1`, `c2`…)를 냅니다. 같은 화면 안의 같은 차이는 `×N`으로 묶이고, **2화면 이상에서 같은 컴포넌트·같은 값으로 나온 차이는 맨 위 공통 후보(`g1`, `g2`…)로 묶입니다.** 공통 후보는 `verdicts.json`의 `groups`에 한 번만 판정하면 그 화면들에 모두 적용되고, 보고서 요약에 "N화면 공통"으로 올라갑니다(2026-11-13 30화면 기준 판정할 항목 430 → 241). 한 화면만 다르게 판정해야 하면 그 화면의 `cN`에 따로 적습니다(화면 판정이 우선).

1. 먼저 **상태가 맞는지** 봅니다. 글자 짝 비율(`글자 짝 a/b`)이 절반 아래이거나 "시안에만 있는 글자"에 고정 문구(제목·탭·버튼)가 많으면 프레임이나 화면 상태(선택된 탭·세그먼트, 열린 메뉴)가 다른 것입니다. 프레임을 바꾸거나 `url`·`actions`를 고쳐 그 화면만 다시 잽니다(2026-11-13 실측에서 3화면이 이 경우였음).
2. 후보를 읽고 **화면마다 캡처를 보며** 판정합니다. `compare`가 판정용으로 본문만 잘라 줄인 캡처를 `<폴더>/view/NN-figma.png`·`NN-impl.png`로 만듭니다(화면당 두 장, 약 1~2k 토큰씩). 캡처를 본 화면은 `verdicts.json`에 `"viewed": true`를 적습니다. 보고서에 화면마다 "캡처 확인 / 규칙 판정"이 표시됩니다.
   - **규칙 판정**(캡처를 보지 않고, 다른 화면에서 캡처로 확인한 패턴을 같은 후보에 적용)은 같은 페이지·같은 컴포넌트의 같은 유형 후보에만 씁니다. 처음 보는 유형, 상·중으로 판정할 후보, 기기가 다른 화면은 캡처를 봅니다. 규칙으로 "오탐"을 일괄 처리하지 않습니다(진짜 차이가 섞여도 보고서에 드러나지 않음).
3. 판정: `상`·`중`·`하`(차이), `x`(오탐), `?`(확인 필요). 오탐의 흔한 원인: 시안과 구현의 감싸는 구조 차이(드롭다운 안쪽 여백 등 같은 결과인데 나뉜 방식만 다름), 데이터 행 수·길이, 계정 상태가 시안과 다름.
4. 원인을 묶습니다: 공용 컴포넌트(`src/shared/ui`)·토큰이 원인인 차이는 화면마다 세지 않고 `summary`에 한 번 적고, 화면에서는 "summary 1과 같은 원인"으로 적습니다. 파일 위치를 알면 `파일:줄`을 메모에 붙입니다. 수정안은 쓰지 않습니다.
5. 후보에 없는데 캡처에서 보이는 차이(아이콘 모양, 요소 누락 등)는 `extra`로 넣습니다. "시안에만 있는 글자"·"구현에만 있는 글자"에서 데이터가 아닌 고정 문구가 있으면 요소 누락·문구 차이로 봅니다.
6. 판정하지 않은 후보는 보고서에 "확인 필요 — 미판정"으로 들어갑니다. 모두 판정합니다.

심각도: **상** 레이아웃 깨짐·요소 누락·다른 컴포넌트, **중** 간격·색·글꼴·모양 지정값 차이, **하** 지정값은 다르지만 화면에서 거의 구분되지 않음.

### 5. 보고

1. `report`로 보고서(`index.html`·`data.js`·`img/`)를 만들고 `open`으로 사용자 브라우저에서 엽니다.
2. `.claude/figma-cache/README.md`에 보고서 한 줄(페이지·날짜·브랜치·경로)을 남깁니다.
3. 브라우저를 닫습니다(`playwright:browser_close`). 로그인도 풀리므로 다른 페이지를 이어서 하면 마지막에 닫습니다.
4. 대화창에는 요약만: 화면별 차이 건수(상·중·하), 공통 원인, 시안 불일치·확인 필요, 검사하지 못한 화면과 이유, 캡처 확인 화면 수 / 규칙 판정 화면 수, 보고서 경로, 걸린 시간.

## 컨텍스트가 요약될 때

보고서 폴더 경로, 확정된 화면 목록(`screens.json`), 진행 단계, 사용자가 정한 범위를 남깁니다. 이어 갈 때는 폴더의 `compare/`·`verdicts.json`을 읽어 끝난 단계를 건너뜁니다.

## 하지 않는 것

- 코드 수정, 테스트 작성, 커밋.
- 화면마다 `figma:get_metadata`·`get_design_context`·브라우저 측정을 따로 부르기(일괄 도구로 대신함). 원인 확인에 특정 노드의 상세가 꼭 필요할 때만 예외로 하나씩 부릅니다.
- 시안에 없는 상태(빈 상태·에러 등)를 임의 기준으로 판정하기. "시안 없음"으로 적습니다.
- Figma 토큰·브라우저 MCP를 쓸 수 없는데 통과로 간주하기. 멈추고 보고합니다.
