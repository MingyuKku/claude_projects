# 마이페이지 · 계정 설정 `/mypage/account`

> 화면은 구현돼 있습니다. 이 문서는 **코드로 알 수 없는 계약·결정·함정과 아직 남은 일(목 데이터, 백엔드, 기획·정책 확인)** 만 남깁니다. 구조·props·파일 구성은 코드를 읽습니다(`pages/mypage-account`, `features/*`, `entities/account`).
> Figma 파일 `a4XCjbdpUcHsm71V1ZucPb` "✔️ 마이페이지"(Change log 3.0.4, 2026-10-19). 화면별 문구 원문·디자이너 주석은 로컬 캐시 `.claude/figma-cache/mypage-setting.md`, v2 `/account` 동작·API는 `.claude/figma-cache/v2-account-mileage.md`(로컬 전용, git 제외). 정확한 수치는 §2의 node ID로 Figma MCP를 다시 호출합니다.
> 마이페이지 메뉴는 구독·빅버드 머니·계정 설정입니다. 구독·빅버드 머니는 별도 스펙(`subscribe.md`, `money.md`)입니다.

## 1. 목적과 범위

- 광고주 Master 계정이 자기 정보·회사 정보·정산 계좌·하위 계정(Sub ID)·알림 수신 동의를 관리합니다. v2 `/account`(섹션 세로 나열 + 모달)를 탭 화면으로 바꿨습니다.
- **Master ID와 Sub ID**: Master ID는 광고주(회사) 계정입니다. Master가 직원용 Sub ID를 개설하면 Sub ID가 로그인해 권한을 받은 작업을 합니다. Sub ID 목록에는 Master가 나오지 않습니다.
- **Master(MASTER·ADMIN)와 Sub ID(SUB) 화면을 모두** 만들었습니다. Sub는 Master ID 관리 탭이 **"Sub ID 관리"**(본인 정보)로 이름이 바뀌고 알림 설정 탭이 있으며, 간편 로그인 연동 카드·회원 탈퇴 버튼·회사정보·계좌정보·Sub ID 관리 탭이 없습니다.
- **Sub ID는 마이페이지 > 구독에 들어갈 수 없습니다**(2026-10-22). 빅버드 머니를 Master와 Sub가 공유하는 구조라 구독 상품도 Master가 결제·관리하고 Sub는 이용 권한만 공유받습니다. `/mypage/subscribe`를 주소로 열면 `MypageLayout`이 `/mypage/account`로 `replace` 이동시킵니다. LNB 구독 메뉴의 Sub 비활성은 구독 화면을 구현할 때 함께 적용합니다.
- **로그인 착지점**은 권한과 관계없이 홈(`/`)입니다(2026-10-22 사용자 결정, [../auth/login.md](../auth/login.md)).

### API와 목 데이터 (마이페이지 3종 공통 규칙)

- 공개된 V3 API([docs/mypage-api.md](../../docs/mypage-api.md))의 응답이 화면을 그리기에 충분하면 **API를 연결**합니다(Zod → 트랜스포머 → SWR). 부족하거나 없는 화면만 목 데이터를 씁니다.
- **목 데이터는 화면 구현 확인용으로만** 씁니다. API가 공개되면 목 분기(목 파일, 목을 돌려주는 훅 내부, 임시 코드값)를 **흔적 없이 지웁니다.** 실제 사용자에게 목 데이터가 보이는 상태로 배포하지 않습니다.
- 목을 쓰는 동안 서버에 반영되는 동작(저장·생성·삭제·연동·업로드·동의 변경)은 **성공한 것처럼 보이지 않게** 합니다. 확인 다이얼로그까지는 시안대로 진행하고 마지막 서버 단계에서 "준비 중인 기능입니다." 토스트를 띄운 뒤 값은 바꾸지 않습니다. API를 연결한 동작은 실제로 호출합니다.
- 응답 형태는 추측해 Zod 스키마로 만들지 않습니다. Zod 스키마는 Swagger 필드로만 만들고, 목은 화면용 뷰모델 타입만 둡니다.
- **목은 개발 서버에서만(2026-10-22 사용자 결정, 같은 날의 "배포 보류"를 대체)**: 아래 4곳은 API가 없어 **개발 서버(`pnpm dev`)에서만 목으로 그리고, 빌드(stage·prod)에서는 본문 자리에 공통 `EmptyState`(`construction`, "준비 중인 기능입니다.")를 둡니다.** 분기는 `import.meta.env.DEV`이고, 목 값도 개발 서버에서만 채워 빌드 번들에 들어가지 않습니다. 그래서 계정 설정은 배포를 막지 않습니다. API가 공개되면 목 분기·`DEV` 분기를 실제 훅으로 바꾸고 목 파일을 지웁니다. 목 외 나머지(Master·회사정보·계좌정보·Sub ID 생성·비밀번호·이메일·프로필 이미지·회원 탈퇴)는 실제 API입니다.
  - 빌드 화면: 알림 설정 탭·SUB 본인 정보 탭은 탭 전체가 준비 중(SUB 본인 정보는 현재 값을 읽을 API가 없어 폼을 채울 수 없음). Sub ID 관리 탭은 목록 자리만 준비 중이고 생성 버튼(실제 `POST /sub`)은 남기며, 권한 부여는 열지 않습니다.
  - Sub ID 목록·검색·`useSubAccount`: `features/manage-sub-accounts/model/mock.ts`, `api/use-sub-accounts.ts`
  - 권한·캠페인 할당: `model/mock-permission.ts`, `api/use-sub-account-permissions.ts`(임시 코드값 `lib/use-code-label.ts`, 백엔드 코드 확정 B-6)
  - Sub ID 본인 정보 조회: `entities/account/model/mock-sub-self.ts`, `api/use-sub-self-account.ts`(아이디·담당자명·휴대폰·이메일·가입일이 모두 고정값. 프로필 이미지만 `GET /profile`로 실제 값, 저장은 실제 API)
  - 알림 설정: `features/notification-consent/model/mock.ts`, `api/use-notification-consent.ts`
  - 서버 반영을 막아 둔 동작(준비 중 토스트): Sub ID 삭제 확정, 권한·할당·알림 스위치, 간편 로그인 연동·해제, 휴대폰 인증
  - 위 조회 4곳은 목이라 로딩 단계가 없어 스켈레톤도 없습니다. SWR 훅으로 바꿀 때 §3 "로딩·오류" 기준의 스켈레톤을 함께 넣습니다.

## 3. 확정 결정

### 공통

| 항목 | 결정 |

| 하위 화면 | Sub ID 생성·권한 부여·회원 탈퇴는 쿼리(`panel=create`, `panel=permission&subId=…`, `panel=withdraw`)로 엽니다. 뒤로가기로 닫히고 새로고침해도 유지됩니다. PC는 Sub ID 생성이 오른쪽 인라인 패널(377px, 딤 없음), 권한 부여는 목록 아래 섹션입니다. ### Master ID 관리 / Sub ID 관리(Sub ID 본인)

| 항목 | 결정 |
|---|---|
| 기본 정보 | 아이디·담당자명·휴대폰 번호·이메일·가입일, 읽기 전용(흐린 톤) |
| 정보 수정 | 프로필 이미지, 비밀번호 변경·비밀번호 확인, 휴대폰 번호 + "인증", 이메일. 하단 왼쪽 "회원 탈퇴"(Master만), 오른쪽 "취소"·"저장". 기본 정보의 이메일은 현재 값(읽기 전용)이고 정보 수정의 이메일은 **바꿀 이메일을 입력하는 칸**입니다. 취소는 입력을 불러온 값으로 되돌립니다 |
| 비밀번호 칸 | 빈 칸으로 시작하고 바꿀 때만 입력합니다(시안의 `12345`는 샘플). **현재 비밀번호 입력칸은 없습니다**(시안대로, 서버도 새 비밀번호만 받음). 규칙은 회원가입과 같습니다. 두 칸이 다르면 확인 칸 아래 "비밀번호가 일치하지 않습니다." Master `PUT /password`, Sub `PUT /sub/pw`. 5분 제한(429)과 개인정보 포함 거부는 오류 문구로 처리합니다 |
| 이메일 | 서버가 본인인증(`certIdx`)을 함께 요구하고, `email`을 비워 보내면 기존 이메일이 지워지므로 항상 값을 채워 보냅니다. Sub는 본인인증 없이 값만 보냅니다 |
| 휴대폰 "인증" | KMC 본인인증 팝업(회원가입과 같은 흐름)으로 바꿉니다. 지금은 "준비 중" 토스트입니다(B-12) |
| 프로필 이미지 | Master·Sub 모두 `GET /profile`로 현재 이미지를 읽고, 이미지가 이미 있으면 PATCH·없으면 POST로 올립니다(Sub는 `/sub/profile`, 서로 상대 경로는 403). 파일 규칙은 서버 한도 확인(B-5) 전까지 JPG·PNG 10MB. 조회가 실패하는 Sub를 대비해 저장한 이미지는 그 화면에서만 계속 보입니다 |
| 회원 탈퇴 | **Master만** 버튼을 그리고 Sub는 그리지 않습니다. 흐름은 v2와 같습니다: ① 약관 화면 → ② "동의 및 탈퇴하기" → ③ 비밀번호 확인(`POST /check/pw`, `result: true`가 일치) → ④ `PUT /exit`(**`POST /transfer/false`는 v3에서 필요 없음**) → ⑤ 완료 안내 → `useLogout`(`GET /logout`, 실패해도 진행) 후 로그인 화면. PC·TAB은 460×650 중앙 다이얼로그(딤), MO는 전체 화면(하단 고정 버튼 한 쌍). 약관 전문은 v2와 같은 **서비스 이용약관**(`entities/terms`의 `service`, 6조 회원탈퇴 포함)이고 시안 MO 약관 박스의 개인정보처리방침 문구는 자리표시자라 따르지 않습니다. v2의 "약관동의" 체크박스와 "아니요/예"는 "동의 및 탈퇴하기" 버튼 하나로 합쳐진 것이 시안입니다. **③·⑤는 시안이 없어 v3 임의 구성**입니다: ③은 안내문 + 비밀번호 한 칸(보기 토글) + "취소"·"탈퇴하기"(v2는 두 칸이나 뒤 칸만 보냈음, 요청 중 연타 방지), 비밀번호가 다르면(`result: false`) 칸 아래 오류, 요청 실패·`exit`의 `result` false는 오류 토스트. ⑤는 제목만의 "확인" 하나짜리 알럿이고 닫기·Esc로 벗어나지 못합니다. 비밀번호 단계는 URL에 남기지 않아 새로고침하면 약관부터 시작합니다. 탈퇴 뒤 서버가 세션을 무효화하는지는 B-11 확인 전입니다 |
| 간편 로그인 연동 | Master만. 카카오·네이버·페이스북·구글·애플 5개 스위치. **페이스북은 v3에서 반드시 연동합니다**(2026-10-21). 지금 앱에는 페이스북 OAuth가 없어 새로 붙여야 합니다(B-10). 켜면 해당 SNS 인증으로 이동하고 돌아오면 결과 토스트, 끄면 확인 알럿(시안에 없어 삭제 알럿과 같은 구조로 새로 둠) 후 해제합니다. 즉시 반영이고 저장 버튼과 무관합니다. 지금은 켜기·확인 모두 "준비 중" 토스트이고 스위치는 원래 값으로 둡니다 |

## 4. 배치

- 파일 첨부 행은 회사정보·계좌정보가 공유하는 `shared/components`의 파일 업로드 입력을 씁니다.
- 데이터를 읽는 훅은 공개 API가 있으면 SWR로 만들고, 목이 필요한 화면만 각 feature의 `model/mock.ts` 목을 돌려줍니다(§1). 세부 구조는 코드를 봅니다.

## 5. 데이터 흐름의 예외

- 공개 API를 연결한 화면은 표준 흐름(Zod → 트랜스포머 → SWR)을 따르고, 목 화면만 SWR·Zod 없이 뷰모델 타입만 둡니다. 어느 쪽이든 UI는 서버 필드명을 쓰지 않습니다.
- 응답 형태가 두 가지(HTTP 상태 + `V3ErrorResponse` / 항상 200 + `result`·`reason`)이고 계좌 등록은 `{result:true, reason:"denied"}`로 거부합니다([docs/mypage-api.md](../../docs/mypage-api.md) §2).
- 폼 상태는 각 feature가 소유하고 탭·하위 화면 상태는 URL 쿼리가 소유합니다.

## 6. 다국어

- 문구 원문은 각 namespace의 `locales/ko.json`이 원본입니다. 탭·카드 제목·라벨은 시안 문구입니다. Figma에 없는 문구(간편 로그인 해제 알럿·저장·생성·삭제 토스트·중복 확인·파일 형식·권한 변경·회원 탈퇴 비밀번호 단계 등)는 사용자 결정으로 추천 문구를 적용했고 임시 문구의 확인은 §7 P-6·P-2에 있습니다.
- 날짜는 `formatDate`. SNS 이름은 서비스 고유 용어가 아니라 브랜드명이라 언어별 통용 표기를 씁니다.
- **서버 값 다국어**는 `.claude/rules/i18n.md` "서버 데이터"를 따릅니다: 상태·유형·권한처럼 종류가 정해진 값은 서버가 **코드(enum)** 로 주고 프론트가 코드마다 번역 키를 둡니다. 목록에 없는 코드가 오면 서버 값을 그대로 표시합니다. 은행명·회사 분류·캠페인명처럼 DB에 쌓이는 값은 그대로 표시하고 다국어는 나중에 정합니다.

| P-2 | 회원 탈퇴 ③ 비밀번호 확인·⑤ 완료 안내는 시안이 없어 v2 흐름·문구를 v3 다이얼로그로 옮긴 임의 구성입니다. 디자인 확인 필요: 문구(안내문 마침표, 버튼 "탈퇴하기", 오류 토스트), 진행 중 캠페인·미정산 시 탈퇴 차단(v2에 없음, 약관 6조 4항만) | 구현함(시안 나오면 교체) |
| P-3 | **회사정보 입력 형식.** v2는 연락처를 숫자만 11자, 사업자 등록 번호를 숫자만 10자로 제한했고 통신판매번호는 3칸(연도 4자리 - 지역(한글 4자 이하) - 일련번호 5자리 이하)이었음. v3 시안은 세 항목 모두 **한 칸**이고 샘플은 하이픈 포함("02-1234-5678", "123-45-67890", 서버 예시 "2024-서울강남-00000"). 형식 제한 여부(숫자만·하이픈 자동 삽입·통신판매번호 구조 검사. 계좌번호는 서버가 "하이픈 없이 숫자만"이라 지금 입력의 하이픈·공백을 지워 보냄), 기존 v2 가입자 데이터(하이픈 없음)와 섞여도 되는지 | 필수 입력 여부만 검사, 입력값 그대로 저장 |
| P-4 | **회사 URL 보정.** v2는 저장할 때 "http"가 없으면 `http://`를 붙였고 v3 회원가입은 도메인 형태를 검사함. `www.example.com`처럼 스킴 없이 입력했을 때 형식 오류로 막을지, 스킴을 붙여 저장할지 | 입력값 그대로 저장 |
| P-5 | **통장사본 파일명 표시.** 사업자 등록증·신고증은 `GET /master` 파일명으로 해결됨. 통장사본은 조회 응답에 파일명이 없음(백엔드 요청 docs §4-10). 서류 다운로드가 필요한지(V3 다운로드 API는 통장 사본만 있음)도 함께 확인 | 이번 화면에서 올린 파일은 파일명, 그 외는 "등록됨" |
| P-6 | **정보 수정 임시 문구·동작.** ① 프로필 이미지 형식·용량 위반 문구(임시: "JPG, PNG 파일만 업로드할 수 있습니다." / "최대 10MB까지 업로드할 수 있습니다."), ② 비밀번호 5분 제한(429)·개인정보 포함 오류 문구(임시: v2 문구), ③ 이메일을 이미 쓰는 계정과 같게 바꿨을 때의 처리(v2는 막지 않았고 시안에 문구 없음), ④ 비밀번호를 바꾼 뒤 v2처럼 재로그인을 요구할지, ⑤ Sub ID 생성 실패 문구·아이디 확인 오류 문구·생성 화면 이미지 형식 문구(임시) | ①②⑤ 임시 문구, ③ 서버 오류면 일반 저장 실패 토스트, ④ 재로그인 요구 없음 |
| P-7 | ① 계좌정보 얼럿에서 **"취소"를 누르면 어디로 가는지**(시안은 얼럿만 있음). ② Sub ID 시안 3종에 **"회원 탈퇴" 버튼이 남아 있는데** Sub에도 탈퇴를 허용할지(기존 결정은 Master만). ③ 회사정보가 비었을 때 계좌정보 탭을 **흐리게 비활성**으로 둘지 | ① 기본 탭(Master ID 관리)으로 이동, ② Sub는 버튼 없음, ③ 탭은 활성이고 진입 시 얼럿 |

### 백엔드

## 8. 범위 밖

- Master가 Sub ID 정보·비밀번호를 고치는 화면(Sub는 본인 비밀번호를 직접 바꿈)
- v2의 브랜드 관리, 캠페인별 담당자 확인(시안 없음)
- 아직 공개되지 않은 API의 연동(B-3), 구독·빅버드 머니 화면
- 다크 모드

## 9. 검증

- `pnpm verify`, 해당하면 `pnpm build`
- 화면 확인(PC 1440·TAB 768·MO 360, 시안 대조, `?lng=en` 등으로 긴 문구 확인)
  1. 탭 전환·잘못된 `?tab=` 대체, 헤더 제목·LNB 활성. SUB는 탭 2개만, SUB가 `/mypage/subscribe`를 열면 계정 설정으로 이동
  2. 정보 수정: 비밀번호 규칙·불일치, 취소로 되돌리기, 저장 토스트. 회원 탈퇴는 실제 계정이 탈퇴되므로 목 응답으로만 확인(Master만 버튼, SUB는 없음)
  3. 간편 로그인 끄기 → 확인 알럿 → "준비 중", 스위치 값 유지
  4. 회사정보 필수 미입력 시 저장 비활성, 파일 형식·용량 오류, 서류 파일명 표시. 회사정보가 비면 계좌정보 탭에서 얼럿(확인 → 회사정보, 취소 → 기본 탭), 계좌정보 은행 Select
  5. Sub ID: 검색·페이지 이동(펼친 권한 부여 섹션 닫힘), 생성(중복 확인 전후 버튼 상태, 아이디 변경 시 재확인), 권한 부여 섹션 열기·행 전환·스위치("준비 중" 후 값 유지), 삭제 알럿, MO 하단 고정 생성 버튼
  6. TAB·MO 하위 화면: 뒤로가기로 닫힘, 새로고침 유지
  7. 알림 설정 토글 → "준비 중" 토스트, 값 유지
- 화면 구현을 마칠 때 목 데이터·목 분기가 남지 않았는지 확인(`grep -rn "mock" src/features src/pages src/entities`). API 공개 전에는 §1 인벤토리 4곳만 남아야 하고, `pnpm build` 결과(`dist/assets`)에 목 값(예: 목 이름·캠페인명)이 없어야 합니다
