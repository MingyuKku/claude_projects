## 1. 목적과 범위

- 광고주가 플랫폼 안에서 쓰는 빅버드 머니를 **무통장 입금(가상계좌)으로 충전**하고, 충전 내역과 사용 내역(인플루언서 계약 비용, 부가 서비스)을 봅니다. v2 `/mileage`(비즈머니, PG 카드 결제)를 대체합니다.
- API와 목 데이터는 [account.md](account.md) §1 규칙을 따릅니다(공개 API가 충분하면 연결, 아니면 목. 목은 화면 구현 확인용이고 구현이 끝나면 흔적 없이 지움). 잔액(`GET /v3/mypage/biz-money`)·충전 내역(`POST …/charge`)·사용 내역(`POST …/usage`)·충전 요청용 초기 데이터(`GET …/init`)가 2026-10-23에 공개돼 **모두 실제 API로 연결**합니다. 거래 상세는 별도 API 없이 충전 내역 항목의 필드(은행·가상계좌·만료·입금일·`receiptUrl`)로 그립니다. 목이 남는 곳은 없습니다(이니시스 결제창 연동은 §3 충전).
- 환불은 추가될 예정이나(기획 확정 2026-10-27) 시안이 아직 없어 범위 밖입니다. 충전 취소는 시안과 정책이 없어 범위 밖입니다(PRD 미정).
- Master(MASTER·ADMIN)와 **빅버드 머니 권한이 있는 Sub ID**가 들어올 수 있습니다(사용자 답변). 권한이 없는 Sub ID에게 LNB 마이페이지 > 빅버드 머니는 흐리게 비활성입니다([main.md](../main.md) "LNB 메뉴 구성과 권한"). 화면 구성은 Master와 같습니다.

### 시나리오

1. 헤더의 "P {보유 금액}" 또는 LNB 마이페이지 > 빅버드 머니로 들어오면 충전 내역 탭이 열립니다. 보유 빅버드 머니와 충전 안내를 봅니다.
2. "충전하기"로 충전 패널을 열고 금액을 입력(또는 빠른 금액)한 뒤 "{금액}원 충전하기"를 누르면 충전 요청이 접수되고, 충전 상세 내역에 "대기 중" 건이 생깁니다. 가상계좌 정보는 그 건의 거래 상세에서 봅니다.
3. 입금이 확인되면 그 건이 "결제 완료"가 되고 보유 금액이 늘어납니다. 기한 안에 입금하지 않으면 기한이 끝난 가상계좌로는 입금할 수 없고, 그 건은 "결제 취소"(서버 값 기준)로 옵니다. 기획 확정(2026-10-27): 취소 건은 내역에 계속 보여 주고, 기한 만료는 "결제 취소"가 아니라 **"미입금" 등으로 표시할 예정**입니다(문구 미확정이라 지금은 "결제 취소" 유지. 서버가 만료와 사용자 취소를 구분해 주는지는 백엔드 확인 필요).
4. 사용 내역 탭에서 캠페인별 차감 내역과 사용 후 잔액을 봅니다.

## 4. 배치와 Public API

## 5. 데이터 흐름의 예외

- 잔액·충전 내역·사용 내역 모두 공개 API를 표준 흐름(Zod → 트랜스포머 → SWR)으로 연결합니다([docs/mypage-api.md](../../docs/mypage-api.md) §2). 사용 내역은 캠페인 값이 없으면 `"-"`, 금액은 부호 포함이고, 목록 기본 `entrySize`가 사용 내역 8·충전 내역 5라 페이지 크기 10을 명시합니다.
- 거래 상세·사용 상세는 별도 API가 없어 목록 항목에서 만듭니다. 응답에 식별자가 없어 주소의 `?id=`는 지금 쪽 안의 순서(0부터)이고 쪽 쿼리와 함께 가리킵니다(식별자는 백엔드에 요청).
- 충전 요청은 V3가 프록시하지 않는 결제 서버(`bigbird-pay-be`)를 프론트가 직접 부르는 예외입니다. 응답 검증은 Zod로 하고 결제창 호출은 `features/charge-bigbird-money` 안에 둡니다.
- 입금 상태는 서버 한글 값(`결제완료`·`대기중`·`결제취소`)을 코드로 매핑해 배지 색·번역 키에 씁니다. 사용 유형 `usageType`(충전·사용·환불·환급)·`usageDetails`(세부 분류, 추가될 수 있음)는 §7 B-5 확인 전까지 코드 매핑 없이 서버 값을 그대로 둡니다.
- 헤더 보유 금액은 이 페이지와 같은 훅(같은 SWR 키)을 써서 충전 복귀 뒤 두 곳이 같이 갱신됩니다.
