## 1. 목적과 범위

- 광고주가 구독 상품(모집형·PICK형)을 비교하고, 구독 중인 상품의 이용량을 보고, 정기결제 카드·구독 결제 상품·결제 내역을 관리합니다. PRD 5.3: 신용카드 정기결제, 월간/연간, 라이브형·어플리에이터형은 "준비중" 노출, 구독 전에도 데모 체험 무제한.
- API와 목 데이터는 [account.md](account.md) §1 규칙을 따릅니다(공개 API가 충분하면 연결, 아니면 목. 목은 화면 구현 확인용이고 구현이 끝나면 흔적 없이 지움). 구독 상품 목록·이용 중인 구독 목록·정기결제 카드(목록·삭제·결제 카드로 등록)·구독 해지·결제 내역(`/v3/mypage/subscription/…`)은 연결했고, 구독 시작(`init` → 결제 서버 `issuance` → 이니시스 정기결제 페이지 → `?result=` 복귀)도 연결했고 2026-10-28 로컬(Caddy로 Stage 도메인 사용, `docs/kmc-local-test.md`)에서 결제가 되어 구독·카드·결제 내역이 서버에 반영되는 것을 확인했습니다. 카드 추가(결제 서버 `cards/register` → 이니시스 카드 등록 페이지 → `?result=success&cardId=…` 복귀)도 연결했습니다. 이용요약 API(보류)만 목입니다(§7 B-1). 구독 목록은 구독 탭의 "구독 중" 표시, 결제내역의 "구독 결제 상품" 표, 이용요약 탭의 기본 상품이 함께 씁니다. 카드 삭제·결제 카드로 등록은 낙관적으로 갱신하고 실패하면 되돌립니다. 결제 내역은 서버가 쪽 나누기·필터를 합니다. 카드 번호는 결제사가 앞 6자리·끝 1자리만 줘서 서버의 마스킹 번호(`1234-56**-****-***7`)를 그대로 표시합니다(시안의 `****-2567`과 다름, 디자인 확인 필요).
- **구독 결제 흐름도 만듭니다**(2026-10-20 사용자 답변). **브랜드형·공구형은 구독 단위에서 통합**되어 구독 상품은 **모집형·PICK형 2개**이고 세부 유형을 고르는 단계는 없습니다. 캠페인을 만들 때는 브랜드형·공구형이 구분되므로, 캠페인 기준으로 나눠 보여 주는 화면(상품 카드 배지·상세보기 설명·이용요약 막대와 하단 카드·계정 설정 캠페인 할당의 "세부 상품")은 시안대로 둡니다(사용자 답변 2026-10-20). 상품은 나중에 늘어날 수 있으므로 상품 목록을 데이터(배열)로 다루고 2개로 고정하지 않습니다. 가격은 정책이 없어 **더미 데이터**이고, 결제 화면 금액 불일치(199,999 / 199,000)는 신경 쓰지 않습니다.
- Master(MASTER·ADMIN)만 들어올 수 있습니다. **Sub ID는 권한과 관계없이 구독에 들어갈 수 없고** LNB 마이페이지 > 구독은 흐리게 비활성입니다(사용자 답변, [main.md](../main.md) "LNB 메뉴 구성과 권한").

### 시나리오

1. LNB 마이페이지 > 구독으로 들어오면 구독 탭(상품 선택)이 열립니다. 월간/연간을 바꿔 보고 상세보기로 상품 설명을 펼칩니다. 구독 중인 상품에는 "구독 중"이 보입니다.
2. "구독하기" → 결제 화면(안내사항 동의) → "결제" → PG 결제창 → 결제 완료 알럿 → 구독 탭.
3. 이용요약 탭에서 모집형/PICK형을 골라 검색·제안 사용량과 월별·일별 이용 차트를 봅니다.
4. 결제내역 탭에서 정기결제 카드를 추가·삭제·기본 카드로 바꾸고, 구독을 해지하고, 결제 내역을 검색·필터합니다. 환불 기능은 제공하지 않습니다(2026-10-29 사용자 결정).

## 4. 배치와 Public API

- `pages/mypage-subscribe`: `MyPageSubscribePage`(탭·쿼리 소유, 셸).
- `entities/subscription`: 상품·구독 상태 뷰모델과 목 데이터, 상품 카드(`SubscriptionPlanCard`)처럼 여러 feature가 쓰는 표시 컴포넌트.
- `features/browse-subscription-plans`: 월간/연간 토글 + 상품 카드 목록 + 상세보기(`SubscriptionPlanList`).
- `features/view-subscription-usage`: 이용요약(`SubscriptionUsageDashboard`). 차트는 `shared/ui/chart`(Recharts) 기반, 캐러셀 페이지 계산은 `lib`.
- `features/manage-billing-cards`: 정기결제 카드(`BillingCardList`).
- `features/manage-subscription`: 구독 결제 상품·해지(`SubscribedProductTable`).
- `features/payment-history`: 결제 내역 목록·필터(`PaymentHistory`). 빅버드 머니 스펙의 충전·사용 내역과 툴바·필터 화면 구조가 같으므로, 공통 부분(검색+기간+Select 툴바, TAB·MO 필터 화면, MO 카드 리스트)은 `shared/components`로 올리는 것을 구현 계획에서 검토합니다.
- `shared/config/routes.ts`에 `mypageSubscribe: "/mypage/subscribe"`.
- 세부 분할·props는 `/plan`에서 정합니다.

## 5. 데이터 흐름의 예외

- 상품·구독·카드·결제 내역·해지는 표준 흐름(Zod → 트랜스포머 → SWR)으로 연동했고, 이용요약만 API가 없어 목 단계입니다(SWR·Zod 없음). 이용요약 API가 나오면 표준 흐름으로 바꾸고 목은 지웁니다. 뷰모델(`SubscriptionPlan`, `Subscription`, `UsageSummary`, `UsageSeries`, `BillingCard`, `SubscribedProduct`, `PaymentRecord`)만 둡니다.
- 결제 상태·결제 수단은 서버 코드값으로 받아 배지 색·번역 키에 매핑해야 합니다. 코드 체계는 백엔드 확인(§7 B-2) 전까지 목 데이터의 임시 코드(`paid`·`refunding`·`refunded`)로 둡니다.

## 6. 다국어

- namespace: `pages/mypage-subscribe`, 각 feature, `entities/subscription`.
- Figma에 없는 문구(한국어 원문, 사용자 결정으로 추천 문구를 적용):

### 백엔드

구독은 v2에 없어 API가 새로 만들어졌습니다. 아래는 백엔드 답변(2026-10-28)으로 확정된 내용입니다.

- **서버 구분:** 조회·카드 관리·해지·결제 내역은 V3(`/v3/mypage/subscription/…`), 결제가 필요한 구독 시작·카드 추가·카드가 있을 때 구독(`change`)은 결제 서버입니다. 모든 구독 API는 마스터 전용이고 Sub ID는 403입니다. 에러는 `{ result: false, reason: 코드 }`입니다.
- **구독 시작(결제 서버 `stage.client.bigbird.co.kr:3101`, 배포·동작 확인 2026-10-28):** `GET …/init`으로 토큰(10분 유효)을 받고 → 결제 서버 `POST /v3/subscription/billing/subscribe/new-card`에 `{ token, productType, billingPeriod, origin, redirectUri }` → 응답 값을 숨은 form에 넣어 `issuanceUrl`로 POST(전체 이동) → 결과는 `{origin}{redirectUri}?result=success&subscriptionId=…` 또는 `?result=fail&reason=코드`로 돌아옵니다. 복귀 도메인(`origin`)은 프론트가 정하고 서버는 검증하지 않습니다(2026-10-29 허용 목록 제거). 금액·주문번호·서명은 서버가 만들고, 머니 충전의 `encryptUserIdx`는 쓸 수 없습니다. 구독 시작 에러 코드: `INVALID_TOKEN`·`INVALID_REQUEST`·`PRODUCT_NOT_AVAILABLE`·`ALREADY_SUBSCRIBED`·`CARD_LIMIT_EXCEEDED`·`CARD_REGISTER_FAILED`·`PAYMENT_FAILED`·`INTERNAL_ERROR`. 첫 카드는 기본 카드가 되고, 첫 결제가 실패하면 카드·구독이 저장되지 않습니다.
- **카드:** `maskedNumber`는 결제사가 앞 6자리·끝 1자리만 줘서 `1234-56**-****-***7` 형식입니다(시안 `****-2567`과 다름, 디자인 확인 필요). 삭제: 결제 중인 구독이 있으면 기본 카드는 409 `DEFAULT_CARD_IN_USE`, 보조 카드는 언제든 가능, 구독이 없거나 모두 해지했으면 기본 카드도 삭제되고 남은 카드가 기본이 됩니다. 없는·남의 카드는 404 `BILLING_CARD_NOT_FOUND`. 결제 카드 변경은 다음 정기결제부터 적용됩니다.
- **해지:** 응답 `{ subscriptionId, productType, canceledAt, serviceEndAt }`. 현재 회차 종료일(`serviceEndAt`)까지 이용 후 끝납니다. 환불 정책 전이라 `requiresReturnPayment`는 없습니다. 이미 해지 409 `ALREADY_CANCELED`, 없는·남의 구독 404 `SUBSCRIPTION_NOT_FOUND`.
- **결제 내역:** 성공한 구독 결제만 최신순, `from`·`to`는 양 끝 포함(KST, `YYYY-MM-DD` 아니면 400). 정기결제는 일시불이라 결제 수단은 `card`, 상태는 `paid`만 옵니다(할부·환불로 거르면 빈 목록). `receiptUrl`은 KG이니시스 카드 매출전표 주소입니다.
- **카드만 등록(Q-4):** 결제 서버에 만들 예정이며 결제사가 결제 없이 카드만 인증하는 방식을 허용하는지 확인 중입니다.
- **이용요약:** 검색·제안 횟수를 기록하는 기능(V3 인플루언서 매칭·마켓)과 한도 정책이 정해진 뒤 개발합니다(보류, 목 유지).

| # | 확인할 내용 | 답 전 처리 |
|---|---|---|
| B-1 | **[일부 배포]** 상품 목록·구독 목록·카드(목록·삭제·기본 변경)·해지·결제 내역은 연동함. 구독 시작(`init` → `issuance` → form POST → `?result=` 복귀)은 연동하고 2026-10-28 로컬(Caddy)에서 결제까지 확인함(결제 서버 CORS는 `https://stage.client.bigbird.co.kr`만 허용이라 localhost·내부 IP에서는 직접 호출 불가). 서버에는 구독 1건·기본 카드 1장·결제 1건(`paid`, `receiptUrl`)이 반영됨. 카드 추가(`cards/register`)도 연동함(2026-10-29 배포, 실결제창 확인 전). 카드가 있을 때 구독(`change`, 404 미배포), 환불, 이용요약(보류)은 대기 | 이용요약만 목 데이터 |

| B-3 | 이용요약 데이터 모양: ① 상품별 요약(검색·제안 `{used, remaining}`, 브랜드형·공구형 지표별 누적, 미구독 여부) ② 시계열(상품·지표·월별/일별·연도·월 쿼리, `{period, brand, groupBuy}[]`와 `availableYears`). 데이터 없는 기간을 0으로 채울지, 미래 기간 생략 여부, 한국 시간 기준 | 목 데이터(`entities/subscription/model/mock.ts`) |
