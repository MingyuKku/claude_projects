# 다국어 (i18next · react-i18next)

지원 언어는 `ko`(기본·fallback), `en`, `ja`, `zh-CN`(간체)입니다. 언어 코드는 BCP 47을 쓰며 v2의 `jp`는 쓰지 않습니다.
화면에 보이는 모든 문구(라벨, 버튼, 안내, 에러, 빈 상태, `aria-label`·`alt`·`placeholder`, `<title>`)는 다국어 대상입니다.

사용법: `import { useTranslation, Trans, formatDate, formatNumber, useLanguage } from "@/shared/i18n"` 후 `const { t } = useTranslation("pages/login")`로 씁니다. `i18next`·`react-i18next`를 직접 임포트하지 않습니다(ESLint). `ko.json` 키를 바꾸면 `pnpm i18n`으로 타입을 다시 생성하고 `pnpm i18n:check`로 검사합니다.

## 파일 배치와 namespace

- 번역은 문구를 쓰는 슬라이스가 소유합니다: `src/{layer}/{slice}/locales/{ko,en,ja,zh-CN}.json`. namespace는 `{layer}/{slice}`입니다(예: `pages/login`).
- 여러 슬라이스가 같이 쓰는 문구(확인·취소·닫기, 공통 검증 문구)만 `src/shared/i18n/locales/`의 `common` namespace에 둡니다.
- 다른 슬라이스의 namespace를 쓰지 않습니다. 같은 문구가 필요하면 `common`으로 올리거나 자기 슬라이스에 따로 둡니다(FSD 격리와 같은 이유).
- `shared/ui`·`shared/components`는 문구를 props로 받거나 `common`만 씁니다.
- `ko.json`이 키의 원본입니다. 키는 `ko.json`에 먼저 추가하고, 네 파일의 키 구성을 항상 같게 유지합니다.

## 키와 문구

- 키는 화면 구조를 따르는 의미 기반 이름입니다: `{section}.{element}[.{state}]` (예: `form.email.label`, `form.email.error.invalid`). 한국어 문장이나 영문 문장을 키로 쓰지 않습니다.
- 문장을 조각내 이어 붙이지 않습니다. 변수는 interpolation(`{{count}}`)으로 넣고, 링크·강조가 섞인 문장은 `<Trans>`로 한 키에 둡니다. 언어마다 어순이 다르기 때문입니다.
- 복수형은 i18next 접미사(`_one`, `_other`)를 씁니다. `ko`·`ja`·`zh-CN`은 `_other`만, `en`은 `_one`·`_other`를 둡니다.
- 서비스 고유 용어는 `docs/prd.md` 용어집의 언어별 표기를 그대로 씁니다.
- Figma에도 스펙에도 없는 문구는 만들지 않고 질문합니다. `en`·`ja`·`zh-CN` 번역 작성 흐름과 간결한 번역 기준은 `i18n-translation.md`(`locales/*.json` 편집 시 자동 로드)에 있습니다.
- 컴포넌트 안의 한국어 리터럴은 금지입니다. 예외는 테스트 파일, `pages/ui-preview` 같은 개발 전용 화면, 개발 서버에서만 렌더되는(`import.meta.env.DEV`) 확인 도구입니다.

## 포맷

- 날짜·숫자·통화는 현재 언어를 넘겨 `Intl`로 포맷합니다. 언어를 넘기지 않는 `toLocaleString()`·`toLocaleDateString()`과 특정 로케일 고정(`"en-US"`, `react-day-picker`의 `ko`)은 쓰지 않습니다.
- 통화 단위는 표시 언어가 아니라 데이터로 정합니다. 언어를 영어로 바꿔도 원화 금액은 원화입니다.

## 서버 데이터

- 사용자가 만든 콘텐츠(인플루언서 이름, 피드 본문, 캠페인 설명)는 번역하지 않습니다.
- **값의 종류가 정해진 서버 데이터**(상태값, 유형, 권한, 결제 수단 등)는 서버가 **코드(enum)**로 주고, 프론트가 코드마다 번역 키를 두어 문구를 보여 줍니다(2026-10-21 팀 결정). 코드 목록은 OpenAPI의 enum이 기준이고, 목록에 없는 코드가 오면 화면을 깨뜨리지 않고 서버 값을 그대로 표시합니다. 코드 대신 한국어 문구만 오는 API는 코드로 달라고 백엔드에 요청합니다.
- **DB에 쌓이는 목록 값**(은행명, 카테고리명, 캠페인명 등 항목이 계속 늘거나 바뀌는 것)은 프론트가 번역을 미리 만들 수 없으므로 서버 값을 그대로 표시합니다. 이런 값의 다국어는 추후 정합니다.
- 스펙 "다국어" 절에는 **서버 코드·값** 표(필드, 코드 또는 그대로 표시, 한국어 표시, 사용 화면)로 정리합니다. 어느 쪽인지 정할 수 없는 값은 사용자에게 질문합니다.

## 에러 문구

- Zod 스키마의 메시지에는 번역 키를 넣고, 렌더할 때 `t()`로 바꿉니다. 모듈 최상단(스키마 정의, 상수)에서 `t()`를 호출하지 않습니다. 언어가 바뀌어도 갱신되지 않기 때문입니다.
- 서버 에러는 에러 코드를 번역 키로 매핑해 보여 줍니다. 서버 메시지 원문을 그대로 노출하지 않습니다.

## 레이아웃

- 영어는 한국어보다 30~40% 길어집니다. 1차 대응은 간결한 번역(`i18n-translation.md`)이고, 그래도 길이 차이는 남으므로 문구가 들어가는 요소에 고정 폭을 주지 않고 가장 긴 언어로 화면을 확인합니다.
- `break-keep`(`word-break: keep-all`)은 `ja`·`zh-CN`에서 줄바꿈 지점을 없애 문구가 넘칩니다. `ko`에만 적용되도록 `:lang(ko)`로 한정합니다.

## 언어 결정과 전환

- URL에 언어 접두어를 두지 않습니다. 순서는 `?lng=`(QA용, `localStorage`에 저장) → `localStorage` → `navigator.languages` → `ko`이며, `zh*`는 번체를 포함해 `zh-CN`으로 매핑합니다.
- Figma에 언어 전환 UI가 없으므로 디자인 없이 전환 UI를 만들지 않습니다. 예외로 개발 서버에서만 보이는 확인용 언어 전환(`widgets/app-shell`의 `DevLanguageSwitcher`, 팀 공유됨)을 둡니다. 배포 빌드에는 포함되지 않으며, 디자인에 전환 UI가 생기면 지웁니다.
- 언어가 바뀌면 `<html lang>`도 함께 바꿉니다.

## 테스트

- 테스트 환경은 `ko` 리소스로 초기화하므로 `getByText`·`getByRole`은 한국어 문구로 찾습니다. 키 문자열로 단언하지 않습니다.
- 포맷·복수형처럼 언어마다 결과가 달라지는 로직은 언어를 바꿔 가며 검증합니다.
